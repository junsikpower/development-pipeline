### DEF-01 — [Critical / 구현실패] 시스템 시계 변경 감지 시 남은 시간이 이중으로 차감된다

- **위반 조항**: EC-04 데이터 처리("남은 시간은 이상 감지 직전 마지막으로 유효했던 계산값으로 고정된다. **임의로 시간을 연장하거나 단축하지 않는다**"), NFR-01, §13.3
- **위치**: `index.html:1097-1098` (`handleClockAnomaly`)
- **실패 케이스**: `EC04-03`, `USR-03`

**원인**
`timerState.remainingSeconds`는 `onTimerTick`(`index.html:1310`)에서 매 tick마다 **이미 경과분이 반영된 값**으로 갱신된다. 그런데 `handleClockAnomaly`는 그 값에서 **앵커 시점부터의 경과 시간을 한 번 더** 빼고 있다.

```js
// index.html:1097-1098
const safeElapsedSec = Math.floor((performance.now() - timerState.perfAnchor) / 1000);
timerState.remainingSeconds = Math.max(1, timerState.remainingSeconds - safeElapsedSec);
```

앵커는 세션 시작·재개·탭 복귀 시점에만 갱신되므로, **세션이 오래 진행될수록 손실이 커진다.**

**재현 결과**

| 시나리오 | 이상 감지 직전 유효 남은시간 | 실제 고정된 값 | 손실 |
|---|---|---|---|
| 25분 Focus 10분 경과 후 시계 +1시간 점프 | 900초 (15:00) | **300초 (05:00)** | 10분 |
| 25분 Focus 8분 경과 후 시계 −2시간 변경 | 1020초 (17:00) | **540초 (09:00)** | 8분 |
| 탭 비활성 5분 후 복귀 시점에 시계 변경 감지 | 1380초 (23:00) | **960초 (16:00)** | 7분 |

시계를 변경하지 않아도 되는 사용자 조작(탭 전환 후 복귀)과 결합되면 손실이 더 커지며, 최악의 경우 `Math.max(1, ...)`에 의해 남은 시간이 1초로 붕괴한다. EC-04가 방지하려던 "시계 변경으로 인한 임의의 시간 단축"이 오히려 감지 로직 자체에 의해 발생한다.

### DEF-02 — [Major / 구현실패] Idle 세션의 변경된 길이가 저장되지 않아 새로고침 시 이전 길이로 되돌아간다

- **위반 조항**: FR-07 Processing("Idle 상태라면 화면 표시와 **다음 시작 시 사용할 길이**가 즉시 새 값으로 갱신된다"), FR-07 AC1/AC3, FR-08 Expected State("새로고침 전후 사용자 관점에서 데이터 손실이나 진행 상황 단절이 없는 상태")
- **위치**: `index.html:1595-1600` (`handleSaveSettings`)
- **실패 케이스**: `FR08-11`, `FR07-10`, `FR07-11`

**원인**
저장(`saveAllState()`)이 `timerState.remainingSeconds` 갱신보다 **먼저** 실행되어, 갱신된 값이 localStorage에 반영되지 않는다.

```js
// index.html:1595-1601
saveAllState();                                    // ← 이 시점의 remainingSeconds 는 아직 옛 값(1500)

if (timerState.sessionState === SESSION_STATE.IDLE) {
  timerState.remainingSeconds = getDurationInSeconds(timerState.sessionType);  // 1980 으로 갱신되나
  renderTimerUI();                                                             // 저장되지 않음
}
```

**재현 결과** (집중 시간 25 → 33분 변경, Idle 상태)

| 항목 | 값 |
|---|---|
| 메모리 상 `remainingSeconds` | 1980 (33:00) ✓ |
| 저장된 `pomodoro_timer_state.remainingSeconds` | **1500** ✗ |
| 저장된 `pomodoro_settings.focusDuration` | 33 ✓ |
| 새로고침 후 타이머 표시 | **25:00** ✗ |
| 새로고침 후 실제 시작한 세션 길이 | **25분** ✗ (설정 화면은 33분으로 표시) |

표시만 어긋나는 것이 아니라, `startTimer()`가 `remainingSeconds` 기준으로 `endTimestamp`를 계산하므로 **실제 세션이 설정값과 다른 길이로 진행된다.** 설정 화면(33분)과 타이머 화면(25:00)이 동시에 모순된 값을 보여준다.

### DEF-03 — [Major / 구현실패] 재접속 복원 시 만료 Focus 세션의 '알림 / 메모 입력'이 누락된다

- **위반 조항**: EC-03 사용자에게 표시되는 결과("이미 지났다면 … '중단 시점의 세션 1회만' **종료 처리(알림/메모 입력 포함)**한 뒤"), §2.3("만료된 세션의 알림은 … 앱이 다시 실행되는 시점에 종료 처리된다"), FR-05 AC1
- **위치**: `index.html:1400-1415` (`restoreApp`)
- **실패 케이스**: `FR08-09`, `FR08-10`

**원인**
복원 경로가 `notifySessionEnd()`를 호출하지 않고, `Memo-Input-Pending` 상태로도 전이하지 않은 채 **빈 메모를 사용자 몰래 확정 저장**한다.

```js
// index.html:1409-1413
logs[dateStr].memos.push({
  time: timeStr,
  memo: ''   // 오프라인 만료 시 빈 메모
});
```

**재현 결과** (25분 Focus 시작 1분 뒤 앱 종료 → 3시간 후 재접속)

| 검증 항목 | 기대(EC-03) | 실제 |
|---|---|---|
| 브라우저 알림 / 소리 / 탭 제목 | 셋 중 최소 하나 발생 | **0건 / 0건 / 변경 없음** |
| 메모 입력 UI | 노출 | **미노출** (`sessionState = idle`) |
| 저장된 메모 | 사용자 입력 대기 | **빈 문자열로 자동 확정** |
| 완료 카운트 1회 / 다음 세션 Idle 대기 | ✓ | ✓ (정상) |

완료 카운트·슬롯·로그 귀속 날짜·Idle 대기는 정상이나, **사용자가 해당 뽀모도로의 작업 내용을 기록할 기회를 영구히 잃는다.** 또한 세션이 종료되었다는 사실 자체를 어떤 수단으로도 통지받지 못한다.

> 참고: EC-03의 "메모 입력 포함"과 BR-02의 "자동 시작 금지"는 상충하지 않는다. BR-02가 FR-03의 자동 시작 원칙을 명시적으로 예외 처리하므로, 올바른 동작은 **메모 입력 → 제출/건너뛰기 → 다음 세션 Idle 대기**이다. (기획 모순 아님)

- **실패 케이스**: `EC05-04`

**원인**
`saveAllState()`는 `SETTINGS → LOGS → TIMER_STATE` 순으로 3개 키를 각각 저장하는데, `safeSaveToStorage`는 **자기 자신의 성공만 보고 전역 `storageState`를 `Synced`로 되돌린다.** 따라서 앞선 키가 실패해도 뒤이은 다른 키의 쓰기 성공이 경고를 지워버린다.

```js
// index.html:911-915
function saveAllState() {
  safeSaveToStorage(STORAGE_KEYS.SETTINGS, settings);      // 성공
  safeSaveToStorage(STORAGE_KEYS.LOGS, logs);              // 실패 → Write-Failed, 배너 표시
  safeSaveToStorage(STORAGE_KEYS.TIMER_STATE, timerState); // 성공 → Synced 로 되돌림, 배너 숨김
}
```

**재현 결과** (`pomodoro_logs` 키만 QuotaExceededError 발생 — 용량 초과 시 가장 먼저 커지는 데이터가 로그이므로 현실적인 시나리오)

| 검증 항목 | 기대 | 실제 |
|---|---|---|
| 로그 키 쓰기 실패 횟수 | > 0 | 5회 (발생) |
| `pomodoro_logs` 저장 결과 | — | **null (전혀 저장되지 않음)** |
| 저장 실패 경고 배너 | 표시 유지 | **미표시** |

완료 기록과 메모가 전혀 저장되지 않고 있는데도 사용자는 정상 저장 중이라고 인지하며, 새로고침 시 해당 데이터를 모두 잃는다. EC-05가 보장하려던 "사용자는 저장 실패 사실을 인지할 수 있다"(§2.3)가 성립하지 않는다.

### DEF-05 — [Minor / 구현실패] 일시정지 시 표시된 남은 시간이 1초 줄어든다

- **위반 조항**: FR-01 AC2("일시정지 후 남은 시간이 변하지 않는다")
- **위치**: `index.html:1141` (`pauseTimer`) vs `index.html:1308` (`onTimerTick`)
- **실패 케이스**: `FR01-03`

**원인**
표시는 `Math.ceil`, 일시정지 스냅샷은 `Math.round`를 사용해 반올림 방식이 불일치한다. 남은 시간의 소수부가 0.5초 미만인 순간(대략 절반의 확률)에 일시정지하면 표시가 1초 뒤로 점프한다.

```js
const remainingSec = Math.max(0, Math.ceil(diffMs / 1000));            // index.html:1308 (표시)
timerState.remainingSeconds = Math.max(1, Math.round(remainingMs / 1000)); // index.html:1141 (일시정지)
```

**재현 결과**: 25분 세션 시작 후 5분 0.6초 시점에 일시정지 → 표시 `20:00` → `19:59`.

사용자 데이터 손실은 없으나, AC의 문언대로 "남은 시간이 변하지 않는다"를 만족하지 않는다.

### DEF-06 — [Minor / 구현실패] 오디오 자동재생이 차단되어 소리가 나지 않는 경우 폴백이 동작하지 않는다

- **위반 조항**: FR-02 AC3("오디오 재생이 실패로 감지되면 탭 제목 변경으로 대체된다"), FR-02 Processing("**소리 알림은 … 주(主) 알림 수단이다**")
- **위치**: `index.html:969` (`initAudioContext`) + `index.html:975-1000` (`playSound`)
- **실패 케이스**: `FR02-06`

**원인**
`audioCtx.resume()`의 Promise 거부를 빈 `catch`로 삼키고, `playSound()`는 컨텍스트 상태와 무관하게 항상 `resolve` 한다. 따라서 `AudioContext`가 `suspended`로 남아 **실제로 아무 소리도 나지 않는 상태**인데도 실패로 감지되지 않아 탭 제목 폴백이 실행되지 않는다.

```js
// index.html:969
audioCtx.resume().catch(() => {});   // 거부가 감지 가능한 신호인데 폐기됨
// index.html:998 — 오실레이터 예약만 성공하면 무조건 resolve
resolve();
```

**재현 결과** (AudioContext `suspended` + `resume()` 거부, Notification 권한 granted)

| 검증 항목 | 기대 | 실제 |
|---|---|---|
| 오디오 컨텍스트 상태 | — | `suspended` (재생 불가) |
| 탭 제목 폴백 | 발생 | **미발생** (`뽀모도로 타이머` 유지) |

`AudioContext` 생성 자체가 불가능한 경우(`FR02-05`)에는 폴백이 정상 동작하므로, **자동재생 정책에 의한 차단 경로만** 누락되어 있다.

> **명세 보완 권고(기획)**: FR-02는 오디오 실패 감지를 "`play()` 호출의 Promise 거부"로 기술하고 있으나, §12.2는 Web Audio API(OscillatorNode) 합성음을 승인된 기술 결정으로 지정하고 있어 `play()`가 존재하지 않는다. Web Audio 경로에서 이에 대응하는 감지 신호는 `AudioContext.resume()`의 Promise 거부 및 `AudioContext.state !== 'running'` 이다. PRD 문언을 이에 맞게 조정하면 구현 기준이 명확해진다. (현 구현의 결함 판정 자체는 FR-02 AC3·Processing만으로 성립한다.)
