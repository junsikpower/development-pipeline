# PRD — 원형 하루 스케줄러 앱 (Circular Daily Scheduler) v3

---

## 1. Project Overview

### 1.1 Project Definition

- 본 프로젝트는 **하루 단위의 계획을 원형(시계형) 계획표 위에 블럭으로 배치하고, 계획된 시각에 로컬 알림을 받는 모바일 스케줄러 앱**이다.
- 핵심 가치는 "시간의 흐름을 목록이 아닌 **면적으로 인지**하게 하는 것"이다. 리스트형 To-do가 답하지 못하는 "내 하루에 빈 시간이 얼마나 남았는가"를 원형 계획표의 빈 호(arc)로 즉시 보여준다.
- 앱의 역할은 (1) 계획 수립 도구, (2) 계획 실행을 유도하는 알림 발송자, (3) 실행 결과를 누적해 보여주는 기록자이다.

### 1.2 Background

- 리스트형 일정 앱은 "몇 시에 무엇을 하는가"는 알려주지만, "하루가 얼마나 채워졌는가"는 알려주지 못한다.
- 초등 교육 현장에서 오랫동안 사용되어 온 원형 생활계획표는 하루 24시간이 유한한 자원임을 직관적으로 드러내는 검증된 표현 방식이다.
- 본 프로젝트는 이 원형 표현을 디지털로 옮기되, 종이 계획표가 제공하지 못하는 **드래그 기반 시간 조정**과 **정시 알림**을 결합한다.

### 1.3 Target Environment

- **대상 플랫폼:** iOS / Android 모바일 애플리케이션.
- **최소 지원 OS 버전:** iOS 15.0 이상 / Android 8.0(API 26) 이상.
  - Android 8.0은 알림 채널(Notification Channel)이 도입된 버전으로, 알림 채널 기반 구현의 하한선이다.
- **실행 조건:** 네트워크 연결 없이 모든 기능이 완결된다.
- **데이터 저장:** 단말 로컬 SQLite 데이터베이스.

#### 1.3.1 알림에 관한 플랫폼 전제 (Platform Premise)

본 프로젝트의 알림 기능은 아래 전제 위에서만 성립한다. 이 전제는 앱이 통제할 수 없는 조건이며, 목표·수용 기준 전반에 예외로 반영된다.

| ID | 전제 |
|----|------|
| PP-01 | **OS에 이미 예약된 알림**은 앱이 실행 중이 아니어도 OS가 발송한다. |
| PP-02 | **앱은 임의의 시점에 자동 실행되지 않는다.** 따라서 예약 큐 갱신은 앱이 실제로 실행되는 순간에만 수행할 수 있다. |
| PP-03 | 알림 발송에는 사용자의 OS 알림 권한이 필요하며, 권한이 없으면 발송되지 않는다. |
| PP-04 | Android 12(API 31) 이상에서 정확 알람 권한이 없으면 발송 시각이 지연될 수 있다. |
| PP-05 | OS의 절전·배터리 최적화 정책은 앱이 통제할 수 없으며, 발송 시각에 영향을 줄 수 있다. |

## 2. Goals & Success Definition

### 2.1 Project Goals

| ID | 목표 |
|----|------|
| G-01 | 사용자가 캘린더에서 임의의 날짜를 선택해, 그 날의 하루 계획을 원형 계획표 위에 블럭으로 구성할 수 있다. |
| G-02 | 배치된 블럭의 시작 시각과 길이를, 자정을 넘는 경우를 포함해 드래그만으로 결정적으로 조정할 수 있다. |
| G-03 | **앱이 OS에 예약을 완료한 알림**은 앱 종료 상태에서도 누락 없이 발송된다. 단 PP-03 ~ PP-05의 조건이 충족되지 않는 경우는 목표의 예외로 한다. |
| G-04 | 예약 지평(BR-06) 내에 존재하는 모든 계획 알림이 예약된 상태로 유지된다. |
| G-05 | 반복되는 하루 패턴을 재입력 없이 재사용할 수 있다. |
| G-06 | 계획 대비 실행 결과가 캘린더 상에서 한눈에 확인된다. |
| G-07 | 서버·계정 없이, 설치 직후부터 즉시 사용 가능하다. |

### 2.2 Goal Completion State

- **G-01 달성 상태:** 캘린더 → 날짜 → 원형 계획표로 이어지는 2-Depth 이동이 완료되고, 기본 제공 블럭 8종과 사용자 생성 블럭이 계획표 위에 배치된 상태.
- **G-02 달성 상태:** 모든 블럭의 시작 시각과 길이가 10분 단위로 정렬되어 있고, 동일 날짜 내에서 시간대가 겹치는 인스턴스가 하나도 존재하지 않는 상태.
- **G-03 달성 상태:** 알림 권한이 부여된 단말에서, 예약 큐에 등록된 알림이 예정 시각에 실제로 단말에 표시된 상태.
- **G-04 달성 상태:** 마지막 큐 갱신 시점 기준으로, 예약 지평 내의 계획 알림 중 미예약 상태로 남은 항목이 0건인 상태.
- **G-05 달성 상태:** 다른 날짜의 논리 블럭이 대상 날짜로 복제되어 동일한 시간 구성이 재현된 상태.
- **G-06 달성 상태:** 각 논리 블럭의 완료 여부가 즉시 기록되고, 해당 날짜의 완료 비율이 캘린더 셀 도트의 불투명도로 반영된 상태.
- **G-07 달성 상태:** 로그인·회원가입·네트워크 연결 없이 앱의 모든 기능이 동작하는 상태.

### 2.3 Overall Success Conditions

프로젝트는 아래를 모두 만족할 때 완성된 것으로 판단한다.

1. 사용자가 앱 설치 직후 어떤 설정도 없이 오늘 날짜의 계획을 수립하고 저장할 수 있다.
2. 알림 권한이 부여된 단말에서, 저장 직후 예약된 알림이 앱을 종료한 상태에서도 예정 시각에 도달한다.
3. 자정을 넘는 수면 블럭이 배치·저장·양일 표시·단일 알림의 전 과정에서 정합성을 유지한다.
4. 네트워크가 완전히 차단된 상태에서 위 1~3이 모두 동일하게 동작한다.
5. 예약 지평을 벗어난 미래 알림이 존재하는 경우, 앱은 이를 유실이 아닌 **미예약 상태**로 관리하고 BR-06의 갱신 절차를 통해 예약 가능한 상태를 유지한다.

> **성공 조건의 경계:** 본 조건은 "앱이 예약을 완료한 알림의 발송"까지를 범위로 한다. 사용자가 예약 지평을 초과하는 기간 동안 앱을 실행하지 않아 큐가 소진된 경우, 그 이후의 알림 미발송은 EC-04에 정의된 정상 동작이며 실패로 판정하지 않는다.

## 4. Functional Requirements

> **용어 정의**
> - **논리 블럭(Logical Block):** 사용자가 인지하는 하나의 활동 단위. 시작 시각과 총 길이를 가진다.
> - **인스턴스(Instance):** 논리 블럭이 특정 날짜에 점유하는 구간을 나타내는 DB 레코드. 자정을 넘지 않는 논리 블럭은 인스턴스 1개, 넘는 논리 블럭은 인스턴스 2개로 저장된다.
> - **대표 인스턴스(Link-Start Instance):** 논리 블럭의 시작 시각을 보유한 인스턴스. `isLinkStart = true`.

### FR-01. 월간 캘린더 메인 화면

**Purpose / Rationale**
- 앱 진입점에서 대상 날짜를 선택하게 하고, 동시에 계획 수립 현황과 실행 현황을 개관하게 한다.

**Trigger**
- 앱 실행 시 최초로 표시되는 화면.

**Input**
- 시스템 현재 날짜
- 날짜별 인스턴스 존재 여부 및 날짜별 달성률

**Processing / Business Rules**
- 월 단위 그리드로 날짜를 표시하며, 전월·익월로 이동할 수 있다.
- 각 날짜 셀은 아래 규칙으로 렌더링한다.
  - **오늘:** 셀 배경을 채워진 원으로 강조한다. 달성률과 무관하게 항상 적용된다.
  - **계획 있음:** 셀 하단에 도트 마커를 표시한다. 도트의 불투명도는 BR-09의 변환식을 따른다.
  - **계획 없음:** 마커를 표시하지 않는다.
- '오늘'과 '계획 있음'은 동시에 성립하며 채워진 원과 도트가 함께 표시된다.
- 셀 내부에 원형 계획표 미니 프리뷰를 렌더링하지 않는다.
- 알림 권한 또는 정확 알람 권한이 미부여 상태이면 화면 상단에 권한 안내 배너를 표시한다(BR-11).

**Output**
- 월간 캘린더 그리드, 날짜별 상태 마커, 필요 시 권한 배너.

**Expected State**
- 사용자는 오늘이 언제인지, 어느 날에 계획이 있는지, 각 날의 달성 정도가 어떠한지를 진입 즉시 식별할 수 있다.

**Acceptance Criteria**
- 오늘 날짜 셀이 다른 셀과 구분되는 채워진 원으로 표시된다.
- 인스턴스가 1개 이상 존재하는 날짜에만 도트가 표시된다.
- 달성률 0%인 날의 도트와 100%인 날의 도트가 서로 다른 불투명도로 표시된다.
- 월 이동 시 각 날짜의 마커 상태가 저장 데이터와 일치한다.

### FR-02. 날짜 선택 및 계획표 진입

**Purpose / Rationale**
- 편집 대상 날짜를 확정하고 편집 화면으로 전환한다.

**Trigger**
- 사용자가 캘린더의 날짜 셀을 탭한다.

**Input**
- 선택된 날짜

**Processing / Business Rules**
- 선택 날짜에 `date`가 일치하는 모든 인스턴스를 조회하여 링에 로드한다. 대표 인스턴스가 아닌 인스턴스(전날에서 이어진 구간)도 함께 표시된다.
- 인스턴스가 0개이면 화면 콘텐츠 상태를 `Empty`로 한다.
- 과거·현재·미래 날짜 모두 선택 및 편집 가능하다.

**Output**
- 선택 날짜의 원형 계획표 편집 화면.

**Expected State**
- 편집 화면 상단에 대상 날짜가 표시되고, 저장된 인스턴스가 모두 반영되어 있다.

**Acceptance Criteria**
- 날짜 탭 시 해당 날짜의 편집 화면으로 이동한다.
- 이전에 저장한 블럭이 저장 당시와 동일한 시각·길이로 표시된다.
- 전날 23:00에 시작해 이어진 구간이 해당 날짜의 00:00 위치에서 표시된다.

### FR-03. 24시간 원형 계획표 렌더링 및 터치 판정

**Purpose / Rationale**
- 하루 전체를 한 화면에 담아 시간 점유를 면적으로 인지하게 한다. 원형 직접 조작이 이 제품의 핵심 조작이므로 터치 판정 규칙을 제품 요구사항으로 확정한다.

**Trigger**
- 편집 화면 진입 시 및 블럭 변경이 발생할 때마다.

**Input**
- 대상 날짜의 인스턴스 목록 (`startMinute`, `durationMinutes`, 스냅샷 속성)

**Processing / Business Rules**

**(1) 각도 매핑**
- 원 한 바퀴(360°)를 24시간으로 매핑한다. **1시간 = 15°, 10분 = 2.5°.**
- 0시를 12시 방향 기준점으로 하고, 시간은 시계 방향으로 진행한다.
- 인스턴스는 `startMinute` 각도에서 시작해 `durationMinutes` 만큼의 중심각을 갖는 호로 그려진다.

**(2) 자정 경계 렌더링**
- 각 인스턴스는 **자기 날짜 링의 범위 안에서만 그려진다.** 자정을 넘는 논리 블럭이 당일 링에서 다음 날 구간까지 계속 그려지지 않는다.
- 자정 경계에서 잘린 인스턴스는 잘린 끝단에 **연속 표식(continuation marker)** 을 표시하여, 해당 활동이 인접 날짜로 이어짐을 나타낸다.
  - `isLinkStart = true` 인스턴스: 종료 끝단(24:00 방향)에 연속 표식.
  - `isLinkStart = false` 인스턴스: 시작 끝단(00:00 방향)에 연속 표식.
- 선택 시 링크 그룹의 총 시작 시각과 총 길이를 표시하여 사용자가 하나의 활동임을 인지할 수 있게 한다.

**(3) 표기 축약**
- 블럭 내 명칭·아이콘 표기는 BR-08의 축약 규칙을 따른다.

**(4) 터치 판정**
- 인스턴스의 터치 영역은 그 인스턴스의 호 영역과 동일하되, 호의 중심선 길이 `L`이 **최소 터치 길이 `minTouch`(44dp / 44pt)** 미만인 경우, **총 터치 영역 길이가 `minTouch`가 되도록** 부족분 `(minTouch − L)`을 양방향에 각각 `(minTouch − L) / 2`씩 배분하여 확장한다. `minTouch`를 양쪽에 각각 더하는 것이 아니다.
- 확장 결과 인접 인스턴스의 터치 영역과 겹치는 구간에서는, **터치 지점의 각도가 더 가까운 쪽 인스턴스**를 선택 대상으로 판정한다.
- 핸들의 터치 영역은 블럭 몸통의 터치 영역보다 우선 판정된다.
- 블럭이 배치되지 않은 각도 영역의 터치는 빈 영역 터치로 판정하며, 선택 해제로 처리한다.

**Output**
- 24시간 원형 계획표와 그 위에 배치된 블럭 호, 연속 표식, 터치 판정 결과.

**Expected State**
- 링 위 어떤 각도도 2개 이상의 인스턴스 호에 의해 동시에 채색되지 않는다.

**Acceptance Criteria**
- 08:00에 시작하고 길이 60분인 블럭이 정확히 15°의 호로 표시된다.
- 전날 23:00~익일 07:00 논리 블럭이, 전날 링에서는 23:00~24:00 구간만, 다음 날 링에서는 00:00~07:00 구간만 그려진다.
- 위 두 인스턴스의 자정 측 끝단에 연속 표식이 표시된다.
- 길이 10분인 블럭을 손가락으로 탭했을 때 선택된다.
- 인접한 두 블럭의 경계 부근을 탭했을 때 더 가까운 쪽이 선택된다.

### FR-04. 블럭 템플릿 제공 및 커스텀 템플릿 생성

**Purpose / Rationale**
- 첫 실행 시 빈 화면 문제를 제거하고, 사용자가 자신의 활동을 자유롭게 정의할 수 있게 한다.

**Trigger**
- 앱 최초 설치 후 첫 실행 (시드 생성)
- 블럭 라이브러리에서 '블럭 추가' 선택 (커스텀 생성)

**Input**
- (시드) 없음
- (커스텀) 명칭, 색상, 아이콘, 기본 길이

**Processing / Business Rules**
- 최초 실행 시 **기본 블럭 8종**을 템플릿으로 생성한다: 잠자기 / 밥먹기 / 씻기 / 공부하기 / 운동하기 / 이동 / 휴식 / 기타.
- 모든 템플릿은 **색상과 아이콘을 동시에** 보유한다. 어느 하나만으로 식별하도록 설계하지 않는다.
- 각 템플릿은 배치 시 적용될 **기본 길이**(10분 배수, 10~1440분)를 가진다.
- 사용자는 명칭·색상·아이콘·기본 길이를 지정하여 커스텀 템플릿을 생성·수정·삭제할 수 있다.
- 기본 템플릿과 커스텀 템플릿은 배치·편집·알림 동작에서 동일하게 취급된다.
- 템플릿 수정·삭제는 기존 인스턴스에 소급 적용되지 않는다(BR-03).
- **템플릿 삭제 시 UI 처리:** 삭제된 템플릿은 라이브러리 목록에서 즉시 제거된다. 해당 템플릿으로 생성된 기존 인스턴스는 스냅샷 속성으로 정상 표시·편집·알림되며, 라이브러리 복귀 경로는 제공하지 않는다.

**Output**
- 블럭 라이브러리에 표시되는 템플릿 목록.

**Expected State**
- 앱 첫 실행 직후에도 라이브러리에 8종이 존재하여 즉시 계획 수립이 가능하다.

**Acceptance Criteria**
- 앱 최초 실행 시 기본 블럭 8종이 라이브러리에 존재한다.
- 커스텀 템플릿 생성 후 라이브러리에서 즉시 사용할 수 있다.
- 템플릿 삭제 후에도 해당 템플릿으로 생성된 기존 블럭이 계획표에서 정상 표시된다.

### FR-05. 블럭 배치 (드래그 앤 드롭)

**Purpose / Rationale**
- 템플릿을 특정 시각에 실체화한다. 배치 제스처와 길이 결정 알고리즘은 제품 동작을 좌우하므로 확정한다.

**Trigger**
- 사용자가 블럭 라이브러리의 템플릿 항목을 링 위로 드래그하여 드롭한다.

**Input**
- 선택된 템플릿, 대상 날짜, 드롭 지점의 각도

**Processing / Business Rules**

**(1) 시작 시각 결정**
- 드롭 지점의 각도를 분으로 환산한 뒤 10분 단위로 스냅한 값이 `startMinute`이 된다.

**(2) 드롭 지점 유효성 검증 (선행 단계, 필수)**
- 길이 산출에 앞서, `startMinute`이 **동일 날짜의 기존 인스턴스가 점유한 반개구간 `[startMinute_i, startMinute_i + durationMinutes_i)` 내부**에 위치하는지 먼저 검증한다.
- 경계 시각(기존 인스턴스의 종료 시각과 정확히 일치하는 지점)은 점유 구간 내부로 간주하지 않으며, 유효한 드롭 지점이다(BR-02의 경계 공유 규칙과 동일).
- 내부에 위치하면 **배치를 즉시 거부**하고 (3) 이하의 가용 길이 산출로 진행하지 않는다(EC-06).
- 이 검증을 통과한 `startMinute`만 유효한 배치 시작점으로 인정한다.

**(3) 길이 결정 (시계 방향 전진 배치)**
- 배치는 항상 `startMinute`에서 **시계 방향으로 전진**한다. 반시계 방향으로 확장하지 않는다.
- 가용 길이 = `startMinute`에서 시계 방향으로 전진할 때 다음 기존 인스턴스의 시작 지점까지의 분(자정을 넘어 다음 날 인스턴스가 있으면 그 시작 지점까지)이며, 최대 1440분으로 제한한다.
- 최종 길이 = **min(템플릿 기본 길이, 가용 길이)** 로 결정한다.
- 최종 길이가 10분 미만이면 배치를 거부한다(EC-06).

**(4) 자정 교차 판정**
- `startMinute + 최종 길이 > 1440` 이면 자정 교차 논리 블럭으로 판정하고 FR-09의 분할 규칙을 적용한다.

**(5) 드래그 중 미리보기**
- 드래그 중 드롭 예정 위치에 반투명 미리보기 호와 함께 시작 시각·종료 시각·길이를 실시간 표기한다.
- 미리보기 단계에서 이미 (2)의 유효성 검증과 (3)의 축소가 적용된 결과를 보여주어, 사용자가 드롭 전 배치 가능 여부와 최종 길이를 확인할 수 있게 한다.
- 드롭 지점이 (2)에 의해 무효로 판정되는 동안에는 미리보기 호를 경고색으로 표시한다(EC-06).

**(6) 인스턴스 생성**
- 템플릿의 명칭·색상·아이콘을 **복제(스냅샷)** 하여 인스턴스를 생성한다.
- 생성된 인스턴스는 편집 세션 상태 `Draft`이며 FR-10의 저장으로 확정된다.

**Output**
- 원형 계획표 위에 생성된 블럭 호.

**Expected State**
- 생성된 인스턴스는 템플릿과 독립적인 자체 데이터를 보유하며, 어떤 기존 인스턴스와도 겹치지 않는다.

**Acceptance Criteria**
- 드롭 지점의 시각이 그대로 블럭의 시작 시각이 된다.
- 기본 길이 60분 템플릿을 가용 공간이 30분인 지점에 드롭하면 30분 길이로 생성된다.
- 가용 공간이 10분 미만인 지점에 드롭하면 블럭이 생성되지 않는다.
- **10:00~11:00을 점유한 기존 인스턴스가 있는 상태에서 10:30 지점에 드롭하면, 가용 길이 산출과 무관하게 배치가 즉시 거부된다.**
- **10:00~11:00을 점유한 기존 인스턴스가 있는 상태에서 정확히 11:00 지점에 드롭하면 유효한 드롭으로 처리된다.**
- 드래그 중 미리보기에 표기된 길이와 드롭 후 생성된 길이가 일치한다.

### FR-06. 블럭 선택 및 블럭 액션

**Purpose / Rationale**
- 선택·이동·완료·삭제·설정이 동일한 블럭 터치 영역에서 발생하므로, 제스처와 액션의 대응 관계를 확정한다.

**Trigger**
- 사용자가 링 위의 블럭 또는 빈 영역을 터치한다.

**Input**
- 터치 제스처 종류 및 터치 지점

**Processing / Business Rules**
- **블럭 탭:** 해당 블럭을 선택 상태로 전환한다. 선택된 블럭에는 양단 핸들이 표시되고, 화면 하단에 블럭 액션 바가 노출된다.
- **블럭 액션 바 구성:** `[완료 체크 토글]` `[알림 설정]` `[삭제]`.
  - 완료 체크는 FR-14를 따른다. 저장되지 않은 `Draft` 인스턴스에는 비활성화된다.
  - 알림 설정은 FR-12의 사전 알림 옵션을 제공한다.
  - 삭제는 링크 그룹 단위로 수행한다(BR-04).
- **블럭 몸통 드래그:** 선택 여부와 무관하게 이동 조작을 시작하며, 대상 블럭을 선택 상태로 전환한다(FR-07).
- **핸들 드래그:** 선택된 블럭에서만 가능하며 길이 조절 조작을 시작한다(FR-07).
- **빈 영역 탭:** 선택을 해제하고 액션 바를 닫는다.
- 동시에 선택될 수 있는 블럭은 최대 1개이다.
- 자정 교차 논리 블럭은 어느 쪽 인스턴스를 탭하더라도 **링크 그룹 전체가 선택**되며, 양쪽 날짜에서 동일한 액션 바가 제공된다.

**Output**
- 선택 표시, 핸들, 블럭 액션 바.

**Expected State**
- 사용자는 어떤 블럭이 선택되었는지 시각적으로 식별할 수 있으며, 의도하지 않은 삭제·완료 처리가 단일 탭으로 발생하지 않는다.

**Acceptance Criteria**
- 블럭 탭 시 핸들과 액션 바가 나타난다.
- 빈 영역 탭 시 선택이 해제된다.
- 블럭 탭만으로는 완료 체크나 삭제가 실행되지 않는다.
- 자정 교차 블럭의 다음 날 구간을 탭해도 동일한 액션 바가 나타난다.

### FR-07. 블럭 이동 및 길이 조절 (자정 경계 포함)

**Purpose / Rationale**
- 원형 좌표에서 자정을 넘는 조작은 값 해석이 다의적이므로, 결정적 규칙을 확정한다. 수면 블럭이 이 제품의 핵심 사례이므로 반드시 명세되어야 한다.

**Trigger**
- 사용자가 블럭 몸통 또는 양단 핸들을 드래그한다.

**Input**
- 드래그 대상(몸통 / 시작 핸들 / 종료 핸들)
- 드래그 궤적의 **누적 회전량**(단순 현재 각도가 아님)

**Processing / Business Rules**

**(1) 편집 좌표계**
- 편집 중 논리 블럭은 `startMinute`(0~1430)과 `durationMinutes`(10~1440)로 표현한다.
- 종료 시각 = `(startMinute + durationMinutes)`. 1440을 초과하는 부분은 다음 날에 속한다.
- 이 표현은 자정 교차 여부와 무관하게 동일하게 적용된다.

**(2) 누적 회전량 해석 원칙 (핵심 규칙)**
- 드래그 값은 손가락의 **현재 각도 위치가 아니라, 드래그 시작 이후의 누적 회전량(부호 있는 각도)** 으로 해석한다.
- 시계 방향 회전은 양(+), 반시계 방향 회전은 음(−)으로 누적한다.
- 이에 따라 "23:00~07:00 블럭의 종료 핸들을 23:50 위치로 끌었을 때"의 해석이 결정된다.
  - **반시계로 끌어온 경우:** `durationMinutes`가 감소하여 **당일 23:50 종료(길이 50분)** 로 해석한다.
  - **시계로 끌어온 경우:** `durationMinutes`가 증가하여 **익일 23:50 종료** 방향으로 해석하되, 1440분 상한에서 정지한다.

**(3) 몸통 드래그**
- `durationMinutes`를 고정하고 `startMinute`만 누적 회전량만큼 변경한다.
- `startMinute`은 0~1439 범위를 순환한다. 즉 블럭을 자정 경계 너머로 자유롭게 이동할 수 있다.

**(4) 시작 핸들 드래그**
- 종료 시각(절대값)을 고정하고 `startMinute`을 변경한다. `durationMinutes`는 그 차이만큼 반대로 변화한다.
- 하한 10분, 상한 1440분에서 정지한다.

**(5) 종료 핸들 드래그**
- `startMinute`을 고정하고 `durationMinutes`만 변경한다.
- 하한 10분, 상한 1440분에서 정지한다.

**(6) 스냅**
- 모든 조작 결과는 **10분 단위로 스냅**된다. 스냅되지 않은 중간값은 저장되지 않는다.

**(7) 24시간 블럭**
- `durationMinutes = 1440`인 논리 블럭은 링 전체를 점유한다. 이 상태에서 다른 블럭은 존재할 수 없다.
- 이 블럭의 종료 핸들을 시계 방향으로 더 끌어도 1440분에서 정지하며, 반시계 방향 드래그로만 길이가 감소한다.
- `startMinute`이 0이 아닌 24시간 블럭은 자정을 교차하므로 FR-09에 따라 2개 인스턴스로 분할된다. `startMinute`이 0인 경우에만 단일 인스턴스로 저장된다.

**(8) 자정 교차 블럭의 링크 갱신 규칙**
- 조작은 항상 **논리 블럭 단위**로 수행된다. 사용자가 어느 쪽 인스턴스의 핸들을 잡았는지와 무관하게, 조작 결과는 논리 블럭의 `startMinute`과 `durationMinutes`에 반영된다.
- 조작 종료 시 논리 블럭을 FR-09의 분할 규칙에 따라 **재분할하여 두 인스턴스를 다시 산출**한다. 두 인스턴스의 값을 개별적으로 조정하지 않는다.
- 예: D일 23:00~24:00(60분) + D+1일 00:00~07:00(420분) 논리 블럭에서 D+1일 쪽 종료 핸들을 08:00까지 끌면, 논리 블럭은 `start=1380, duration=540`이 되고 재분할 결과는 D일 60분 + D+1일 480분이 된다.
- 재분할 결과 다음 날 구간의 길이가 0이 되면 링크를 해제하고 단일 인스턴스로 저장한다.

**(9) 드래그 중 표기**
- 조작 중 시작 시각·종료 시각·총 길이를 실시간 표기하며, 종료 시각이 다음 날에 속하는 경우 그 사실을 함께 표기한다.

**Output**
- 변경된 시각과 길이가 반영된 블럭 호.

**Expected State**
- 조작 종료 후 모든 값이 10분 배수이고, 동일 날짜 내 겹침이 없으며, 링크 그룹의 두 인스턴스 길이 합이 논리 블럭의 총 길이와 일치한다.

**Acceptance Criteria**
- 몸통 드래그 시 블럭 길이가 변하지 않는다.
- 몸통 드래그로 블럭을 자정 경계 너머로 이동할 수 있다.
- 종료 핸들을 반시계로 끌면 길이가 감소하고, 시계로 끌면 증가한다. 동일한 각도 위치라도 회전 방향에 따라 결과가 다르다.
- 길이가 10분 미만 또는 1440분 초과로 변경되지 않는다.
- 자정 교차 블럭의 어느 쪽 핸들을 조작하든 두 인스턴스 길이 합이 총 길이와 일치한다.

### FR-08. 겹침 검증 및 되돌리기

**Purpose / Rationale**
- "특정 시각에 무엇을 하기로 했는가"의 답이 항상 하나가 되도록 데이터 정합성을 보장한다.

**Trigger**
- 배치 또는 드래그 조작 중 다른 인스턴스와 시간대가 중첩될 때.

**Input**
- 조작 중 논리 블럭의 잠정 분할 결과, 관련 날짜(D 및 D+1)의 기존 인스턴스 목록

**Processing / Business Rules**
- **검증 단위:** 겹침 검증은 **날짜별 인스턴스 구간 단위**로 수행한다. 모든 인스턴스는 `startMinute + durationMinutes ≤ 1440`을 만족하므로, 날짜별 구간 비교만으로 링크 블럭을 포함한 전체 겹침을 완전히 검증할 수 있다.
- **판정:** 동일 `date` 내에서 두 인스턴스의 반개구간 `[startMinute, startMinute + durationMinutes)`가 교집합을 가지면 겹침이다. 경계 시각 공유(A 종료 = B 시작)는 겹침이 아니다.
- 자정 교차 조작 시에는 D일과 D+1일 **양쪽 모두**를 검증 대상으로 한다.
- **드래그 중:** 겹침이 발생하면 조작 상태를 `DragConflict`로 전환하고 겹침 구간을 경고색(적색)으로 실시간 표시한다.
- **드래그 종료:** 겹침 상태에서 손을 떼면 해당 논리 블럭을 **마지막 유효 상태로 롤백**한다. 인접 블럭을 밀어내지 않는다.
- **배치 시:** 배치는 FR-05 (2)의 드롭 지점 유효성 검증과 (3)의 길이 축소 알고리즘을 함께 적용해야만 겹침 없는 결과가 보장된다. 드롭 지점이 기존 인스턴스 내부이면 (2)에서 즉시 거부되고, 유효한 드롭 지점이더라도 축소 결과가 10분 미만이면 (3)에서 거부된다(EC-06). 두 단계를 모두 통과한 배치만 이 규칙의 검증 없이도 겹침이 없다.

**Output**
- 겹침 경고 표시 또는 원상 복귀한 블럭.

**Expected State**
- 저장 가능한 모든 상태에서 동일 날짜 내 겹치는 인스턴스 쌍이 존재하지 않는다.

**Acceptance Criteria**
- 겹치는 위치로 드래그하는 동안 경고색이 표시된다.
- 겹친 상태에서 손을 떼면 블럭이 직전 유효 상태로 복귀한다.
- 인접 블럭의 값이 조작 결과로 변경되지 않는다.
- 자정 교차 블럭을 다음 날 기존 블럭과 겹치도록 늘리면 겹침으로 판정된다.

### FR-09. 자정 교차 논리 블럭의 분할 저장 및 링크 관리

**Purpose / Rationale**
- 수면 블럭은 본질적으로 자정을 넘는다. "날짜별 계획표" 데이터 모델을 유지하면서 하나의 활동으로 취급하기 위한 규칙을 확정한다.

**Trigger**
- 논리 블럭의 `startMinute + durationMinutes > 1440`이 되는 모든 시점(배치·이동·길이 조절·복사).

**Input**
- 논리 블럭의 `date`, `startMinute`, `durationMinutes`

**Processing / Business Rules**

**(1) 분할 규칙 (결정적)**
- 인스턴스 A (대표): `date = D`, `startMinute = s`, `durationMinutes = 1440 − s`, `isLinkStart = true`
- 인스턴스 B: `date = D+1`, `startMinute = 0`, `durationMinutes = s + dur − 1440`, `isLinkStart = false`
- 두 인스턴스는 동일한 `linkId`를 공유한다.

**(2) 대표 인스턴스 식별 규칙**
- 링크 그룹의 **대표는 `isLinkStart = true`인 인스턴스**이며, 그룹당 정확히 1개 존재한다.
- 논리 블럭의 시작 시각 = 대표 인스턴스의 `date` + `startMinute`.
- 논리 블럭의 총 길이 = 그룹 내 모든 인스턴스의 `durationMinutes` 합.
- 알림 예약, 완료 상태, 사전 알림 설정은 **대표 인스턴스에만 저장**되며, 비대표 인스턴스는 이 값을 보유하지 않고 대표를 참조한다.

**(3) 링크 단위 조작**
- 삭제·이동·길이 조절·완료 체크·알림 설정은 링크 그룹 전체를 단위로 수행한다.
- 삭제는 그룹 내 모든 인스턴스를 **단일 트랜잭션**으로 제거한다(BR-12).

**(4) 링크 해제**
- 재계산 결과 다음 날 구간의 길이가 0이 되면 인스턴스 B를 제거하고 인스턴스 A의 `linkId`를 해제하여 단일 인스턴스로 전환한다.

**(5) 알림**
- 링크 그룹당 시작 알림은 대표 인스턴스의 시작 시각 기준 **1회만** 발생한다. 분할로 인한 D+1일 00:00 추가 알림은 발생하지 않는다.

**Output**
- 두 날짜에 분산 저장된 인스턴스와 링크 관계.

**Expected State**
- 링크 그룹의 인스턴스 길이 합이 항상 논리 블럭 총 길이와 일치하고, 대표 인스턴스가 정확히 1개이다.

**Acceptance Criteria**
- 23:00 시작 480분 블럭이 D일 60분(대표) + D+1일 420분으로 저장된다.
- 어느 쪽 인스턴스를 삭제해도 두 인스턴스가 함께 제거된다.
- 링크 그룹의 알림이 23:00 기준 1회만 예약된다.
- 길이를 60분으로 줄이면 D+1일 인스턴스가 제거되고 단일 인스턴스가 된다.

### FR-10. 계획 저장 및 이탈 확인

**Purpose / Rationale**
- 드래그로 구성한 계획이 오조작으로 소실되는 것을 방지하고, 저장의 원자성을 보장한다.

**Trigger**
- 사용자가 저장 버튼을 누르거나, 편집 화면에서 뒤로 가기를 시도한다.

**Input**
- 현재 편집 세션의 인스턴스 목록, 변경 여부 플래그

**Processing / Business Rules**

**(1) 저장 대상**
- 저장 대상은 **블럭의 배치·시각·길이·삭제·사전 알림 설정**이다.
- **완료 체크는 저장 대상이 아니다.** 완료 체크는 FR-14에 따라 즉시 커밋되며 변경 여부 판정(`Dirty`)에 포함되지 않는다.

**(2) 저장 절차**
- 저장 실행 시 아래를 **단일 트랜잭션**으로 처리한다(BR-12).
  1. 겹침 검증 (FR-08)
  2. 대상 날짜 D 및 링크로 인해 영향받는 D+1일 인스턴스의 반영
  3. 커밋
- 검증 실패 시 트랜잭션을 실행하지 않고 사용자에게 원인을 표시한다.
- 커밋 성공 시점에 저장은 성공으로 확정된다.

**(3) 알림 예약과의 분리**
- 커밋 성공 후 FR-11의 예약 큐 갱신을 트리거한다.
- **예약 큐 갱신 실패는 저장 실패로 처리하지 않는다.** 알림 예약은 계획 데이터로부터 파생되는 데이터이므로, 계획은 저장된 상태로 유지하고 알림 오류만 별도로 고지한다(EC-10).

**(4) 이탈 확인**
- 뒤로 가기 시점에 **미저장 변경이 존재하는 경우에만** "저장하지 않고 나가시겠습니까?" 확인 다이얼로그를 표시한다.
- 변경이 없으면 확인 없이 즉시 이탈한다.
- 이탈을 선택하면 편집 세션의 변경을 폐기한다. 이미 커밋된 완료 체크는 폐기 대상이 아니다.

**Output**
- 저장 완료 상태, 또는 이탈 확인 다이얼로그.

**Expected State**
- 커밋 이후 DB의 해당 날짜 데이터가 화면 상태와 일치하며, 부분 저장 상태가 존재하지 않는다.

**Acceptance Criteria**
- 저장 버튼을 누르지 않고 이탈 후 재진입하면 블럭 배치가 변경 전 상태로 표시된다.
- 완료 체크만 변경하고 이탈하면 확인 다이얼로그가 표시되지 않으며, 완료 상태는 유지된다.
- 자정 교차 블럭 저장 시 D일과 D+1일 레코드가 함께 반영되거나 함께 반영되지 않는다.

### FR-11. 알림 롤링 예약 및 예약 지평 관리

**Purpose / Rationale**
- 앱은 임의 시점에 자동 실행되지 않으므로(PP-02), 예약 큐 갱신은 앱이 실제 실행되는 순간에만 가능하다. 예약 대상을 한정하되, 큐 소진 이전에 사용자를 앱으로 되돌릴 수단을 함께 제공하여 알림 연속성을 앱이 통제 가능한 범위에서 최대화한다.

**Trigger (갱신 트리거)**
- T1: 계획 저장 커밋 성공 직후
- T2: 앱이 포그라운드로 진입할 때 (콜드 스타트 및 백그라운드 복귀 포함)
- T3: 사용자가 알림을 탭하여 앱에 진입할 때
- T4: 앱이 **포그라운드**에서 실행 중인 상태로 자정을 경과할 때

> **주의:** T4는 앱이 백그라운드에 있는 동안에는 성립하지 않는다. PP-02·OS-10에 따라 앱은 백그라운드에서 임의로 실행되지 않으므로, 백그라운드 상태의 자정 경과를 감지하는 로직은 존재하지 않는다. T4는 사용자가 자정 전후로 앱을 포그라운드에 열어 둔 드문 경우에만 성립하는 부가적 갱신 기회이며, 알림 연속성의 보장 수단으로 삼지 않는다. 연속성의 실질적 보장 수단은 T2(포그라운드 진입)와 예약 갱신 리마인더(아래 (4))이다.

**Input**
- 현재 시각 이후의 모든 계획 알림 후보 (대표 인스턴스의 시작 알림 + 사전 알림)

**Processing / Business Rules**

**(1) 예약 상한**
- OS에 등록되는 대기 알림은 **최대 50개**이다.
- 50은 OS가 강제하는 상한이 아니라 **앱이 자체적으로 설정한 보수적 상한**이다. iOS는 앱당 대기 로컬 알림에 개수 제한이 존재하고 Android는 정확 알람 사용에 별도 제약이 있으므로, 양 플랫폼에서 안전한 공통 상한으로 50을 채택한다(TD-09).

**(2) 예약 대상 선정**
- 현재 시각 이후의 알림 후보를 시각 오름차순으로 정렬하고 앞에서부터 최대 **49개**를 예약한다.
- 시작 알림과 사전 알림은 각각 별도 항목으로 산입된다.
- 이미 지난 시각의 후보는 예약하지 않는다.

**(3) 예약 지평 (Scheduling Horizon)**
- **예약 지평** = 마지막 갱신 시점에 예약된 항목 중 가장 늦은 발송 시각.
- 예약 지평 이후의 알림 후보는 **미예약(Unscheduled)** 상태로 DB에 보존되며, 다음 갱신 시 예약 대상이 된다. 이는 유실이 아니다.

**(4) 예약 갱신 리마인더**
- 50개 중 마지막 1개 슬롯은 **예약 갱신 리마인더**로 사용한다.
- 미예약 후보가 1건 이상 존재하는 경우에만 예약하며, 발송 시각은 예약 지평의 마지막 계획 알림 발송 시각으로 한다.
- 이 알림은 사용자에게 앱을 열어 이후 일정 알림을 이어서 예약하도록 안내하는 내용을 담는다.
- 미예약 후보가 없으면 이 슬롯을 예약하지 않으며, 계획 알림을 최대 50개까지 예약한다.

**(5) 갱신 절차**
- 갱신 트리거 발생 시 기존 예약을 전량 취소하고 (1)~(4)에 따라 재예약한다.
- 삭제되거나 시각이 변경된 블럭의 예약은 이 과정에서 자연히 정리된다.

**Output**
- OS 알림 스케줄러에 등록된 최대 50개의 예약 항목.

**Expected State**
- 예약 항목 수가 항상 50개 이하이고, 모든 항목이 미래 시각이며, 미예약 후보가 존재하면 예약 갱신 리마인더가 함께 예약되어 있다.

**Acceptance Criteria**
- 계획 저장 직후 해당 계획의 미래 알림이 예약 큐에 존재한다.
- 예약 항목 수가 50개를 초과하지 않는다.
- 알림 후보가 60개일 때 49개의 계획 알림과 1개의 예약 갱신 리마인더가 예약된다.
- 알림 후보가 20개일 때 예약 갱신 리마인더가 예약되지 않는다.
- 블럭 삭제 후 다음 갱신 시 해당 알림이 예약 큐에서 제거된다.
- 앱이 종료된 상태에서도 예약된 알림이 예정 시각에 도달한다.

### FR-12. 알림 시점 설정 및 알림 내용

**Purpose / Rationale**
- 알림 피로도를 억제하면서 준비 시간이 필요한 활동에 사전 고지 수단을 제공한다. 알림 문구는 이 제품의 주요 출력물이므로 요구사항으로 확정한다.

**Trigger**
- 사용자가 선택된 블럭의 액션 바에서 `[알림 설정]`을 연다.

**Input**
- 사전 알림 옵션 (없음 / 5분 전 / 10분 전)

**Processing / Business Rules**

**(1) 알림 시점**
- 기본값은 **논리 블럭 시작 시각 정각 1회**이다.
- 논리 블럭별로 사전 알림을 5분 전 또는 10분 전으로 설정할 수 있다.
- 사전 알림을 설정해도 시작 알림은 유지된다. 즉 논리 블럭당 최대 2개의 알림 항목을 갖는다.
- 사전 알림 설정은 논리 블럭 단위이며 대표 인스턴스에 저장된다. 템플릿에 소급 적용되지 않는다.
- 사전 알림 설정은 계획 편집의 일부이므로 FR-10의 저장 버튼으로 확정된다.

**(2) 알림 내용**
- **시작 알림**
  - 제목: 블럭 명칭(스냅샷 값)
  - 본문: 시작 시각과 종료 시각을 포함한 안내
- **사전 알림**
  - 제목: 블럭 명칭(스냅샷 값)
  - 본문: 시작까지 남은 시간(5분 또는 10분)을 포함한 안내
- **예약 갱신 리마인더**
  - 제목: 앱 명칭
  - 본문: 이후 일정 알림을 계속 받으려면 앱을 열어야 한다는 안내
- 사전 알림과 시작 알림은 서로 다른 문구로 구분되어야 한다.

**(3) 동일 시각 알림 처리**
- 겹침 금지 정책에 따라 동일 시각에 시작하는 블럭은 최대 1개이지만, A의 사전 알림과 B의 시작 알림이 동일 시각이 될 수 있다.
- 이 경우 두 알림을 **병합하지 않고 각각 별도 알림으로 발송**한다.

**(4) 알림 탭 동작**
- 계획 알림을 탭하면 해당 논리 블럭의 날짜 편집 화면으로 진입한다.
- 예약 갱신 리마인더를 탭하면 캘린더 화면으로 진입한다.
- 어느 경우든 T3 트리거로 예약 큐 갱신이 수행된다.

**Output**
- 블럭별 알림 설정 상태 및 발송되는 알림.

**Expected State**
- 사전 알림이 설정된 논리 블럭은 예약 후보 2개를 갖는다.

**Acceptance Criteria**
- 사전 알림 미설정 블럭은 시작 시각에만 알림이 발송된다.
- 10분 전 사전 알림 설정 시 시작 10분 전과 시작 시각에 각각 알림이 발송된다.
- 두 알림의 본문이 서로 다르다.
- 알림 제목에 블럭 명칭이 표시된다.

### FR-13. 다른 날짜 계획 복사

**Purpose / Rationale**
- 반복 루틴의 재입력 부담을 제거한다. 자정 교차 블럭의 복사 범위를 확정하여 결과가 결정적이 되도록 한다.

**Trigger**
- 사용자가 편집 화면에서 '다른 날짜에서 불러오기'를 선택하고 원본 날짜를 지정한다.

**Input**
- 원본 날짜 S, 대상 날짜 T (현재 편집 중인 날짜)

**Processing / Business Rules**

**(1) 복사 단위 및 대상 선정 규칙**
- 복사 단위는 **논리 블럭**이다.
- 복사 대상은 **대표 인스턴스의 `date`가 S와 일치하는 논리 블럭**으로 한정한다.
- 따라서 S일 링에 표시되지만 **전날에서 이어져 온 구간(`isLinkStart = false`)은 복사하지 않는다.**
  - 근거: 이를 복사하려면 대상 날짜 T의 전날(T−1)에 소급 생성이 필요하며, 이는 사용자가 편집 중이지 않은 날짜의 데이터를 변경하는 예측 불가능한 부수효과를 낳는다.

**(2) 복사 속성**
- 복제 대상: 명칭·색상·아이콘 스냅샷, `startMinute`, 총 `durationMinutes`, 사전 알림 설정.
- **완료 상태는 복제하지 않는다.** 복제된 논리 블럭은 미완료로 생성된다.

**(3) 기존 계획 처리**
- 대상 날짜 T에 기존 인스턴스가 존재하는 경우, 부분 병합은 단일 점유 원칙(BR-02) 하에서 정합성을 보장할 수 없으므로 **T일 인스턴스를 전량 삭제한 후 교체**한다.
- 파괴적 동작이므로 실행 전 확인 다이얼로그를 표시한다.
- T일에 표시되던 전날 이월 구간(`isLinkStart = false`) 또한 그 링크 그룹 전체와 함께 삭제된다.

**(4) 자정 교차 블럭의 복사 결과**
- 원본이 자정 교차 논리 블럭이면 T일 기준으로 FR-09의 분할 규칙을 재적용하여 T일 인스턴스와 T+1일 인스턴스를 생성한다.
- **T+1일 충돌 처리:** 생성될 T+1일 구간이 T+1일의 기존 인스턴스와 겹치는 경우, **해당 논리 블럭만 복사 대상에서 제외**하고 나머지는 복사한다. T+1일의 기존 데이터는 변경하지 않는다.
- 제외가 발생하면 복사 완료 시 제외된 블럭의 개수와 명칭을 사용자에게 고지한다.

**(5) 확정**
- 복제 결과는 편집 세션에 반영되며, DB 확정은 FR-10의 저장 버튼을 따른다.

**Output**
- 원본과 동일한 구성이 반영된 편집 화면 및 제외 발생 시 고지.

**Expected State**
- 복사 후 T일의 논리 블럭 구성이 S일에서 시작하는 논리 블럭 구성과 동일하다.

**Acceptance Criteria**
- 복사 실행 후 대상 날짜의 블럭 구성이 원본 날짜에서 시작한 블럭 구성과 일치한다.
- S일에 표시되던 전날 이월 구간이 T일에 생성되지 않는다.
- 기존 블럭이 있는 날짜에 복사 시 확인 다이얼로그가 표시된다.
- T+1일과 충돌하는 자정 교차 블럭이 있으면 해당 블럭만 제외되고 고지된다.
- 복제된 블럭의 완료 상태가 모두 미완료이다.

### FR-14. 실행 완료 체크 및 달성률 표시

**Purpose / Rationale**
- 계획 도구를 실행 기록 도구로 확장한다. 완료 체크는 계획 편집이 아니라 실행 사실의 기록이므로 저장 시점을 계획 편집과 분리한다.

**Trigger**
- 사용자가 선택된 블럭의 액션 바에서 완료 체크를 토글한다.

**Input**
- 대상 논리 블럭, 완료 여부

**Processing / Business Rules**

**(1) 저장 시점**
- 완료 체크는 토글 즉시 DB에 커밋된다(**즉시 저장**).
- 완료 체크는 `Dirty` 판정 대상에 포함되지 않으며, 저장 버튼이나 이탈 확인의 영향을 받지 않는다.
- 근거: 완료 체크는 시간 배치에 영향을 주지 않아 겹침 검증이 불필요하고, 캘린더 즉시 반영 요구와 일관된다.
- **`Draft` 상태의 미저장 인스턴스에는 완료 체크를 제공하지 않는다.** 저장 후 활성화된다.

**(2) 저장 위치와 링크 처리**
- 완료 상태는 **대표 인스턴스에만 저장**된다.
- 자정 교차 논리 블럭의 완료 체크는 링크 그룹 전체에 적용되며, 양쪽 날짜에서 동일한 완료 상태로 표시된다.

**(3) 달성률 산출**
- **날짜별 달성률 = (해당 날짜 링에 표시되는 논리 블럭 중 완료된 수) ÷ (해당 날짜 링에 표시되는 논리 블럭 수)**
- 링에 표시되는 논리 블럭에는 대표 인스턴스가 그 날짜인 블럭과, 전날에서 이월된 블럭이 모두 포함된다. 즉 하나의 자정 교차 논리 블럭은 D일과 D+1일 달성률 계산에서 **각각 1개씩** 집계된다.
- 이는 의도된 정책이다. 달성률의 의미는 **"그 날 링 위에 존재하는 활동 중 완료된 비율"** 이며, 자정 교차 활동은 실제로 두 날 모두의 시간을 점유하므로 양일 모두에 반영되는 것이 링의 시각적 사실과 일치한다.
- 따라서 하나의 수면 활동을 완료 처리하면 D일과 D+1일 달성률이 모두 상승한다.
- 논리 블럭 수가 0인 날짜의 달성률은 정의되지 않으며, 도트를 표시하지 않는다.

**(4) 표시**
- 완료된 블럭은 링에서 미완료 블럭과 구분되는 시각 처리를 받는다.
- 날짜별 달성률은 캘린더 셀 도트의 불투명도로 반영된다(BR-09).

**Output**
- 블럭의 완료 표시 및 캘린더 도트 불투명도 변화.

**Expected State**
- 완료 체크 결과가 즉시 DB에 반영되고 캘린더 복귀 시 반영되어 있다.

**Acceptance Criteria**
- 완료 체크 후 저장 버튼을 누르지 않고 이탈해도 완료 상태가 유지된다.
- 완료 체크만 변경한 경우 이탈 확인 다이얼로그가 표시되지 않는다.
- 자정 교차 블럭을 완료 처리하면 양쪽 날짜에서 완료로 표시된다.
- 전체 논리 블럭을 완료한 날짜의 도트가 최고 불투명도로 표시된다.

## 5. Business / System Rules

### BR-01. 시간 그리드 규칙
- 저장되는 모든 `startMinute`과 `durationMinutes`는 **10분의 배수**이다.
- `startMinute` 범위: 0 ~ 1430. `durationMinutes` 범위: 10 ~ 1440.
- 인스턴스는 항상 `startMinute + durationMinutes ≤ 1440`을 만족한다.
- 각도 변환식: `각도 = (분 ÷ 1440) × 360°`. 10분 = 2.5°.

### BR-02. 단일 점유 규칙
- 동일 날짜의 임의 시각은 최대 1개의 인스턴스에만 점유된다.
- 검증은 반개구간 `[startMinute, startMinute + durationMinutes)` 교집합으로 수행한다. 경계 공유는 충돌이 아니다.
- 이 규칙을 위반하는 상태는 저장될 수 없다.

### BR-03. 템플릿-인스턴스 불변 규칙
- 인스턴스는 생성 시점 템플릿 속성(명칭·색상·아이콘)의 복제본을 보유한다.
- 템플릿의 수정·삭제는 기존 인스턴스에 소급 적용되지 않는다.
- 템플릿이 삭제된 인스턴스도 정상 표시·편집·알림된다.

### BR-04. 링크 그룹 규칙
- 자정 교차 논리 블럭은 `linkId`를 공유하는 2개 인스턴스로 저장되며, 그중 `isLinkStart = true`인 인스턴스가 **대표**이다.
- **논리 블럭 단위 속성**(시작 시각, 총 길이, 사전 알림 설정, 완료 상태, 알림 예약 연결)은 대표 인스턴스에만 저장된다.
- 삭제·이동·길이 조절·완료 체크·알림 설정은 링크 그룹 전체를 단위로 수행한다.
- 링크 그룹당 시작 알림은 1회만 발생한다.

### BR-05. 논리 블럭 수와 인스턴스 수의 구분
- **인스턴스 수**는 DB 레코드 수이며, 자정 교차 블럭은 2를 기여한다.
- **논리 블럭 수**는 사용자가 인지하는 활동 수이며, 자정 교차 블럭은 1을 기여한다.
- 삭제·이동·완료·알림은 **논리 블럭 단위**로 취급한다(BR-04).
- **날짜별 달성률은 "그 날짜 링에 표시되는 논리 블럭"을 모집단으로 한다**(FR-14 (3)). 이 모집단에는 대표가 그 날짜인 블럭과 전날 이월 블럭이 모두 포함되므로, 하나의 자정 교차 논리 블럭이 두 날짜의 모집단에 각각 1개씩 포함된다. 이는 BR-04와 상충하지 않으며, 조작 단위(논리 블럭 1개)와 날짜별 표시 단위(날짜마다 1개씩)를 구분한 결과이다.

### BR-06. 알림 예약 상한 및 예약 지평 규칙
- OS에 등록되는 대기 알림은 **항상 최대 50개**이며, 이는 OS 상한이 아니라 앱이 정한 보수적 공통 상한이다.
- 미예약 후보가 존재하면 50개 중 1개를 예약 갱신 리마인더로 사용하고, 계획 알림은 49개까지 예약한다.
- **예약 지평**은 마지막 갱신 시점 기준 가장 늦은 예약 항목의 발송 시각이다.
- 예약 지평 이후의 후보는 미예약 상태로 DB에 보존되며 유실로 간주하지 않는다.
- 예약 큐 갱신은 앱이 실제로 실행되는 순간(T1~T4)에만 수행된다. 앱은 임의 시점에 자동 실행되지 않는다(PP-02).

### BR-07. 알림 보장 범위 규칙
- 앱의 알림 책임 범위는 **"OS에 예약이 완료된 알림"** 까지이다.
- 아래는 앱의 실패로 판정하지 않는 정상 동작이다.
  - 알림 권한 미부여로 인한 미발송 (PP-03)
  - Android 정확 알람 권한 미부여로 인한 지연 (PP-04)
  - OS 절전 정책으로 인한 지연 (PP-05)
  - 예약 지평 초과 후보의 미예약 상태 (BR-06)
- 아래는 앱의 실패로 판정한다.
  - 예약이 완료된 알림이 권한·OS 정책 문제가 없음에도 발송되지 않는 경우
  - 갱신 트리거 발생 시 예약 가능한 후보가 예약되지 않는 경우
  - 삭제·변경된 블럭의 알림이 취소되지 않고 발송되는 경우

### BR-08. 협소 블럭 표기 축약 규칙
- 판단 기준값은 **호 중심선 길이** `L = r_mid × θ` (r_mid = 링 트랙 중심 반지름, θ = 블럭 중심각(rad))이다. 고정 분(minute) 임계값이 아닌 실제 렌더링 길이로 판단하므로 화면 크기·글꼴 크기·해상도가 달라도 결과가 결정적이다.
- 필요 길이 = 렌더링될 텍스트 폭 + 아이콘 폭 + 내부 여백.
- 적용 순서:
  1. `L ≥ 명칭 폭 + 아이콘 폭 + 여백` → **명칭 + 아이콘** 표시
  2. `L ≥ 아이콘 폭 + 여백` → **아이콘만** 표시
  3. 그 외 → **색상만** 표시
- 축약 여부와 무관하게, 블럭 선택 시 액션 바 또는 상세 표기를 통해 명칭을 확인할 수 있어야 한다.

### BR-09. 캘린더 마커 표현 규칙
- 논리 블럭이 1개 이상 존재하는 날짜에만 도트를 표시한다.
- 도트의 **불투명도 = 0.3 + 0.7 × 달성률** (선형 변환). 달성률 0% → 0.30, 50% → 0.65, 100% → 1.00.
- 색상(색상값 자체)과 크기는 달성률에 따라 변하지 않으며, 불투명도만 변한다.
- 오늘 날짜의 채워진 원 강조는 달성률과 무관하게 항상 적용되며 도트와 병존한다.

### BR-10. 터치 판정 규칙
- 블럭 터치 영역은 호 영역과 동일하되, 호 중심선 길이 `L`이 최소 터치 길이 `minTouch`(44dp / 44pt) 미만이면, **총 터치 영역 길이가 `minTouch`가 되도록** 양방향 각각 `(minTouch − L) / 2`만큼 확장한다. (예: `L = 10dp`인 블럭은 양쪽에 각 17dp씩 추가되어 총 44dp가 되며, 양쪽에 44dp씩 더해 98dp가 되는 것이 아니다.)
- 확장으로 인접 블럭 터치 영역과 겹치는 구간은 터치 각도가 더 가까운 블럭에 귀속된다.
- 핸들 터치 영역은 몸통 터치 영역보다 우선한다.
- 자정 교차 블럭의 두 인스턴스는 터치 시 동일한 논리 블럭으로 판정된다.

### BR-11. 권한 고지 규칙
- 알림 권한 또는 Android 정확 알람 권한이 미부여 상태이면 **캘린더 화면과 날짜 편집 화면 양쪽 모두**에 권한 안내 배너를 표시한다.
- 배너는 미충족 권한의 종류와 그로 인한 영향을 명시하고, OS 설정 화면으로 이동하는 경로를 제공한다.
- 권한 미부여 상태에서도 계획의 배치·저장·복사·완료 체크는 정상 동작한다.

### BR-12. 트랜잭션 및 무결성 규칙
- 겹침 검증(BR-02)은 **애플리케이션 계층의 저장 직전 검증**으로 수행한다. SQLite 스키마 제약으로는 구간 겹침을 표현할 수 없으므로 DB 제약에 의존하지 않는다.
- 아래 작업은 각각 **단일 트랜잭션**으로 처리하여 부분 반영을 허용하지 않는다.
  - 계획 저장 (D일 및 링크로 영향받는 D+1일 인스턴스 반영)
  - 링크 그룹 삭제 (그룹 내 전체 인스턴스 제거)
  - 날짜 복사 (기존 인스턴스 삭제 + 신규 인스턴스 생성)
- 삭제는 **물리 삭제**이며 soft-delete 레코드를 남기지 않는다.
- 알림 예약은 DB 트랜잭션 범위 밖의 파생 작업이며, 실패해도 DB 트랜잭션을 롤백하지 않는다.

### BR-13. 로컬 전용 규칙
- 모든 사용자 데이터는 단말 로컬 DB에만 존재한다.
- 앱은 어떤 사용자 데이터도 외부 서버로 전송하지 않는다.
- 계정 식별자가 존재하지 않으므로 데이터 귀속 주체는 '단말'이다.

## 6. State & Data Model

### 6.1 System / UI States

화면 상태는 **상호 배타적인 단일 상태 집합이 아니라, 서로 직교하는 상태 차원의 조합**으로 정의한다. 이는 "드래그 중 겹침"이 `Dragging`인지 `Conflict`인지 모호해지는 문제를 제거하기 위함이다.

| 차원 | 값 (상호 배타) | 적용 화면 |
|------|----------------|-----------|
| **콘텐츠(Content)** | `Empty` (논리 블럭 0개) / `Loaded` (1개 이상) | 편집 화면 |
| **변경(Change)** | `Clean` (미저장 변경 없음) / `Dirty` (미저장 변경 있음) | 편집 화면 |
| **조작(Interaction)** | `Idle` / `Selected` / `Dragging` / `DragConflict` | 편집 화면 |
| **처리(Process)** | `Idle` / `Saving` / `SaveError` | 편집 화면 |
| **권한(Permission)** | `PermissionOK` / `PermissionWarning` | 캘린더 화면 + 편집 화면 (공통) |

**규칙**
- 드래그 중 겹침 상태는 조작 차원의 `DragConflict` 단독으로 표현한다. `Dragging`과 동시 성립하지 않는다.
- 모든 블럭을 삭제하면 콘텐츠 차원은 `Loaded → Empty`로 되돌아간다. `Loaded`는 논리 블럭 1개 이상을 의미하며, 블럭 0개인 `Loaded` 상태는 존재하지 않는다.
- 변경 차원은 콘텐츠 차원과 독립이다. 블럭을 전부 삭제한 직후는 `Empty + Dirty`이다.
- 권한 차원은 화면 전환과 무관하게 앱 전역에서 동일하게 유지된다(BR-11).

### 6.2 Data States

데이터 상태는 **DB 영속 상태**와 **파생/세션 상태**를 구분한다.

**(1) DB 영속 상태 — 실제 레코드**

| 상태 | 의미 |
|------|------|
| `Stored` | 인스턴스 레코드가 DB에 존재함 |
| (레코드 없음) | 삭제되었거나 아직 저장되지 않음. 물리 삭제이므로 `Deleted` 레코드는 남지 않는다(BR-12) |

**(2) 편집 세션 상태 — 화면 메모리상의 논리 상태**

| 상태 | 의미 | 전이 |
|------|------|------|
| `Draft` | 이번 세션에서 생성되어 아직 커밋되지 않음 | 배치·복사로 생성 → 저장 시 `Committed`, 이탈 시 소멸 |
| `Modified` | 저장된 인스턴스를 이번 세션에서 변경함 | 저장 시 `Committed`, 이탈 시 원복 |
| `Committed` | 화면 상태와 DB가 일치함 | 재변경 시 `Modified` |

**(3) 알림 파생 상태 — 예약 큐로부터 계산되는 상태**

| 상태 | 의미 | 전이 조건 |
|------|------|-----------|
| `Unscheduled` | 미래 알림 후보이나 예약 지평 밖이라 미예약 | 갱신 시 지평 안에 들어오면 `Scheduled` |
| `Scheduled` | OS 예약 큐에 등록됨 | 발송 시 `Fired`, 취소·재계산 시 `Unscheduled` |
| `Fired` | 발송 완료 | 종료 상태 |

- 50개를 초과하는 미래 후보는 `Unscheduled`에 머물다가, 갱신 트리거(T1~T4) 발생 시 예약 지평이 앞으로 이동하면서 `Scheduled`로 전환된다. 즉 전환 시점은 **갱신 트리거 시점**이며, 임의로 발생하지 않는다.
- 알림 파생 상태는 DB에 저장되지 않고 매 갱신 시 계산된다.

**(4) 시간 및 기록 상태 — 각각 독립**

| 차원 | 값 |
|------|-----|
| 시간 | `Upcoming` (시작 시각 미도래) / `Passed` (경과) |
| 기록 | `Incomplete` / `Completed` |

- 기록 차원은 시간 차원과 독립이다. `Upcoming + Completed`(사전 완료 체크)가 가능하며, 이는 정상 상태이다.
- 따라서 데이터 상태는 단일 선형 전이 그래프가 아니라 위 4개 차원의 조합으로 표현된다.

### 6.3 Core Data Entities

**BlockTemplate (블럭 템플릿)**

| 속성 | 의미 |
|------|------|
| `id` | 템플릿 식별자 |
| `name` | 블럭 명칭 |
| `color` | 표시 색상 |
| `icon` | 표시 아이콘 |
| `defaultDurationMinutes` | 배치 시 기본 길이 (10~1440, 10분 배수) |
| `isSeed` | 기본 제공 8종 여부 |

**BlockInstance (블럭 인스턴스)**

| 속성 | 의미 | 비고 |
|------|------|------|
| `id` | 인스턴스 식별자 | |
| `date` | 소속 날짜 | |
| `startMinute` | 해당 날짜 내 시작 분 (0~1430, 10분 배수) | |
| `durationMinutes` | 해당 날짜 내 점유 길이 (10~1440, 10분 배수) | `startMinute + durationMinutes ≤ 1440` |
| `nameSnapshot` / `colorSnapshot` / `iconSnapshot` | 생성 시점 템플릿 속성 복제본 | |
| `linkId` | 자정 교차 링크 그룹 식별자 (미교차 시 null) | |
| `isLinkStart` | 대표 인스턴스 여부 | 링크 그룹당 정확히 1개가 true |
| `preNotifyMinutes` | 사전 알림 (null / 5 / 10) | **대표 인스턴스에만 유효** |
| `isCompleted` | 완료 여부 | **대표 인스턴스에만 유효** |

- `endMinute` 대신 `durationMinutes`를 보유한다. 이로써 24시간 블럭(`durationMinutes = 1440`)이 시작=종료의 모호함 없이 표현되며, 자정 교차 여부는 논리 블럭 재구성 시점에 `linkId` 유무로 판정된다.
- 비대표 인스턴스의 `preNotifyMinutes`와 `isCompleted`는 사용하지 않으며, 조회 시 항상 대표 인스턴스의 값을 참조한다.

**NotificationScheduleItem (알림 예약 항목)**

| 속성 | 의미 |
|------|------|
| `id` | 예약 식별자 |
| `instanceId` | **대표 인스턴스**의 id. 자정 교차 블럭도 대표 인스턴스에만 연결한다 |
| `fireAt` | 발송 예정 시각 |
| `type` | `start` / `pre` / `horizonReminder` |

- `type = horizonReminder`인 항목은 `instanceId`를 갖지 않는다.

**관계**

| 관계 | 카디널리티 | 비고 |
|------|-----------|------|
| `BlockTemplate → BlockInstance` | 1 : N (복제 관계) | 참조 무결성 제약 없음 (BR-03) |
| `linkId → BlockInstance` | 1 : 2 | 자정 교차 시에만 존재 |
| **대표 BlockInstance → NotificationScheduleItem** | **1 : 0..2** | 비대표 인스턴스는 예약 항목을 갖지 않는다 |
| 비대표 BlockInstance → NotificationScheduleItem | 1 : 0 | 규칙으로 강제 |

- 위 관계 정의에 따라 링크 그룹 전체가 보유할 수 있는 예약 항목은 최대 2개(시작 1 + 사전 1)이며, 4개가 될 수 없다.

## 7. Data Lifecycle & Persistence

### 7.1 Data Ownership
- 계정 개념이 없으므로 모든 데이터의 귀속 주체는 **앱이 설치된 단말**이다.

### 7.2 Storage
- 저장 위치: 단말 내부 **로컬 SQLite 데이터베이스**.
- 저장 범위: 블럭 템플릿, 블럭 인스턴스, 사전 알림 설정, 완료 상태.
- 알림 예약 항목은 DB에 영속화하지 않고 갱신 시마다 계산한다.
- **무결성 보장 계층:** 겹침 금지는 애플리케이션 계층의 저장 직전 검증으로 보장한다. SQLite 스키마 제약으로는 구간 겹침을 표현할 수 없다(BR-12).
- **트랜잭션 범위:** 저장·삭제·복사는 각각 단일 트랜잭션이며, 자정 교차 링크의 두 인스턴스는 동일 트랜잭션에 포함된다(BR-12).
- 서버 저장소를 사용하지 않는다.

### 7.3 Synchronization
- 서버가 존재하지 않으므로 동기화 정책이 존재하지 않는다.
- 기기 간 데이터 이전은 개발 범위에서 제외된다(OS-02, OS-09).

### 7.4 Retention
- 계획 데이터는 사용자가 삭제하지 않는 한 기한 없이 보존된다.
- 과거 날짜 데이터도 삭제되지 않으며 캘린더에서 열람 가능하다.
- 알림 예약 항목은 파생 데이터이며 독립적으로 보존되지 않는다.

### 7.5 Deletion
- 블럭 삭제는 **논리 블럭 단위**이며, 링크 그룹의 모든 인스턴스를 **단일 트랜잭션**으로 제거한다. 한쪽만 삭제되는 부분 실패는 트랜잭션 롤백으로 방지한다(BR-12).
- 삭제는 물리 삭제이며 soft-delete 레코드를 남기지 않는다.
- 인스턴스 삭제 후 다음 예약 큐 갱신 시 해당 알림 예약이 정리된다.
- **템플릿 삭제:** 라이브러리에서 제거되며 기존 인스턴스에는 영향이 없다. 스냅샷을 보유하므로 고아 인스턴스라는 상태가 존재하지 않으며 별도 정리 작업이 필요하지 않다(BR-03, FR-04).
- **앱 삭제 시 로컬 DB가 함께 제거되어 모든 데이터가 소실된다.** 서버 백업이 없으므로 앱 자체의 복구 수단은 없다.
- 로그아웃·계정 탈퇴 개념은 존재하지 않는다.

## 8. Error & Edge Cases

### EC-01. 알림 권한 거부
- **발생 조건:** 사용자가 OS 알림 권한을 거부했거나 이후 비활성화함.
- **시스템 상태:** `PermissionWarning`. 알림이 발송되지 않는다.
- **사용자 표시:** 캘린더 화면과 편집 화면 모두에 안내 배너를 표시하고 OS 설정 이동 경로를 제공한다(BR-11).
- **데이터 처리:** 계획의 저장·편집·복사·완료 체크는 정상 동작하며 알림 설정값도 보존된다.
- **복구 시점:** 사용자가 설정에서 권한을 허용하고 앱으로 돌아오면, **앱 포그라운드 복귀(T2) 시점에 즉시 예약 큐를 재생성한다.** 별도의 사용자 조작이나 다음 저장을 기다리지 않는다.
- **최종 상태:** 알림을 제외한 전 기능 사용 가능. 권한 허용 시 즉시 예약 복구.

### EC-02. Android 정확 알람 권한 미보유
- **발생 조건:** Android 12(API 31) 이상에서 정확 알람 권한이 부여되지 않음.
- **시스템 상태:** `PermissionWarning`.
- **대체 동작 (확정):** 알림 기능을 중단하지 않고 **부정확 알람(inexact alarm)으로 계속 예약한다.** 알림은 발송되나 시각이 지연될 수 있다.
- **사용자 표시:** 배너에 "현재 알림이 예정 시각보다 늦게 도착할 수 있음"과 권한 부여 시 정시 발송된다는 사실을 명시하고 설정 이동 경로를 제공한다.
- **데이터 처리:** 계획 데이터에 영향 없음.
- **복구 시점:** 권한 부여 후 앱 포그라운드 복귀(T2) 시 정확 알람으로 재예약한다.
- **최종 상태:** 권한 부여 시 정시, 미부여 시 지연 가능. 어느 경우에도 알림 자체는 제공된다.

### EC-03. 예약 지평 초과 (예약 큐 포화)
- **발생 조건:** 미래 알림 후보가 예약 상한을 초과함.
- **시스템 상태:** 정상. 앞선 49개 계획 알림 + 1개 예약 갱신 리마인더가 예약되고, 나머지는 `Unscheduled`.
- **사용자 표시:** 오류로 표시하지 않는다. 예약 지평 도달 시 예약 갱신 리마인더가 발송된다.
- **데이터 처리:** 미예약 후보도 DB에 그대로 보존된다. **유실이 아니다.**
- **복구:** 갱신 트리거(T1~T4) 발생 시 예약 지평이 이동하며 순차 예약된다.
- **최종 상태:** 예약 항목 50개 이하가 유지되고, 가까운 미래 알림이 우선 보장되는 상태.

### EC-04. 장기 미실행으로 인한 예약 지평 소진
- **발생 조건:** 사용자가 예약 지평을 초과하는 기간 동안 앱을 실행하지 않음.
- **시스템 상태:** 예약 큐가 소진되어 이후 알림이 예약되지 않음.
- **완화 수단:** 예약 지평의 마지막 계획 알림 시점에 **예약 갱신 리마인더**가 발송되어 사용자를 앱으로 유도한다(FR-11 (4)).
- **사용자 표시:** 예약 갱신 리마인더 알림.
- **데이터 처리:** 계획 데이터는 손실되지 않는다.
- **복구:** 앱 실행 즉시(T2) 큐를 재계산하여 알림 예약을 복원한다.
- **최종 상태:** 예약 지평 이후의 알림 미발송은 **BR-07에 따라 정상 동작이며 실패로 판정하지 않는다.** 앱 실행 시 즉시 복원된다.

> **"앱 종료"와 "장기 미실행"의 경계:** 앱 종료 상태에서도 **예약 지평 내의 알림은 보장된다.** 보장의 경계는 시간 경과가 아니라 **예약 지평**이며, 지평을 넘어선 시점부터 보장이 종료된다.

### EC-05. 드래그 중 시간 겹침
- **발생 조건:** 조작 중 논리 블럭의 분할 결과가 D일 또는 D+1일 기존 인스턴스와 중첩됨.
- **시스템 상태:** 조작 차원 `DragConflict`.
- **사용자 표시:** 겹침 구간을 경고색으로 실시간 표시.
- **데이터 처리:** 겹친 상태의 값은 저장되지 않는다.
- **롤백:** 손을 떼는 즉시 마지막 유효 상태로 롤백한다.
- **최종 상태:** 겹침이 없는 유효한 배치 상태.

### EC-06. 배치 공간 부족 / 드롭 지점 무효

두 가지 발생 조건을 구분하되 사용자 표시와 처리는 동일하게 적용한다.

- **발생 조건 A (드롭 지점 무효):** 드롭 지점(`startMinute`)이 이미 기존 인스턴스가 점유한 반개구간 내부에 위치함 (FR-05 (2)). 예: 10:00~11:00을 점유한 블럭이 있는 상태에서 10:30에 드롭.
- **발생 조건 B (가용 길이 부족):** 드롭 지점은 유효하나, 그 지점에서 시계 방향 가용 길이가 10분 미만임 (FR-05 (3)).
- **시스템 상태:** 두 조건 모두 인스턴스가 생성되지 않음.
- **사용자 표시:** 드래그 중 미리보기 호를 **경고색으로 표시하여 드롭 불가 상태를 사전 고지**하고, 드롭 시 짧은 토스트로 "이 위치에는 블럭을 놓을 수 없습니다"를 표시한다. 조건 A와 B를 사용자에게 구분하여 안내하지 않는다 — 두 경우 모두 "이 위치에는 놓을 수 없다"는 동일한 사실이기 때문이다.
- **자동 제안 여부:** 가장 가까운 빈 공간으로 **자동 이동시키지 않는다.** 사용자의 배치 의도를 임의로 변경하지 않기 위함이다.
- **데이터 처리:** 변경 없음.
- **최종 상태:** 배치 이전 상태 유지. 사용자가 다른 위치로 다시 드롭할 수 있다.

### EC-07. 자정 교차 논리 블럭의 부분 조작 시도
- **발생 조건:** 링크된 두 인스턴스 중 한쪽만 삭제·이동·완료 처리하려는 시도.
- **시스템 상태:** 조작 대상이 링크 그룹 전체로 확장됨(BR-04).
- **사용자 표시:** 두 날짜 모두에 반영된 결과.
- **데이터 처리:** 논리 블럭 단위로 재계산 후 FR-09 규칙에 따라 재분할하여 단일 트랜잭션으로 반영.
- **최종 상태:** 링크 그룹 정합성이 유지된 상태.

### EC-08. 기존 계획이 있는 날짜로의 복사
- **발생 조건:** FR-13 복사 실행 시 대상 날짜 T에 블럭이 이미 존재함.
- **시스템 상태:** 파괴적 동작 대기.
- **사용자 표시:** 기존 계획이 삭제됨을 알리는 확인 다이얼로그.
- **데이터 처리:** 승인 시 T일 인스턴스(전날 이월 구간 포함, 링크 그룹 전체)를 삭제한 후 복제. 취소 시 변경 없음.
- **롤백:** 저장 전이므로 이탈 시 폐기 가능하다.
- **최종 상태:** 원본과 동일한 구성이거나, 복사 이전 상태.

### EC-09. 복사 시 다음 날 충돌
- **발생 조건:** 복사 대상 중 자정 교차 논리 블럭이 있고, 생성될 T+1일 구간이 T+1일 기존 인스턴스와 겹침.
- **시스템 상태:** 해당 논리 블럭만 복사 대상에서 제외됨.
- **사용자 표시:** 복사 완료 후 제외된 블럭의 개수와 명칭을 고지한다.
- **데이터 처리:** T+1일의 기존 데이터는 변경하지 않는다. 나머지 블럭은 정상 복사된다.
- **최종 상태:** 충돌 블럭을 제외한 구성이 T일에 반영된 상태.

### EC-10. 저장 실패 및 알림 예약 실패
- **(A) DB 저장 실패**
  - **발생 조건:** 저장소 용량 부족 등으로 SQLite 트랜잭션이 실패함.
  - **시스템 상태:** 처리 차원 `SaveError`.
  - **사용자 표시:** 저장 실패 사실과 재시도 수단.
  - **데이터 처리:** 트랜잭션 전체를 롤백하여 부분 저장을 남기지 않는다. 편집 중이던 내용은 화면에 유지한다.
  - **최종 상태:** 저장 성공, 또는 편집 내용이 보존된 실패 상태. 데이터가 조용히 유실되는 상태는 허용되지 않는다.
- **(B) 알림 예약 실패**
  - **발생 조건:** DB 커밋은 성공했으나 OS 알림 예약 등록이 실패함.
  - **시스템 상태:** 저장은 성공 상태.
  - **사용자 표시:** "계획은 저장되었으나 알림 예약에 실패했습니다"를 별도로 고지한다.
  - **데이터 처리:** **계획 데이터는 저장 상태로 유지한다.** 저장을 실패로 되돌리지 않는다. 알림은 파생 데이터이기 때문이다(BR-12).
  - **복구:** 다음 갱신 트리거(T1~T4)에서 재예약을 시도한다.
  - **최종 상태:** 계획은 저장되고 알림만 미예약인 상태.

### EC-11. 협소 블럭 표기 불가
- **발생 조건:** 호 중심선 길이가 명칭 또는 아이콘 렌더링 필요 길이에 미달함.
- **시스템 상태:** 정상.
- **사용자 표시:** BR-08의 3단계 축약 규칙 적용. 터치 영역은 BR-10에 따라 최소 44dp/44pt로 확장 유지된다.
- **데이터 처리:** 영향 없음.
- **최종 상태:** 축약 표기되나 선택·조작·명칭 확인이 모두 가능한 상태.

### EC-12. 계획이 없는 날짜 진입
- **발생 조건:** 논리 블럭이 0개인 날짜에 진입.
- **시스템 상태:** 콘텐츠 차원 `Empty`.
- **사용자 표시:** 빈 원형 계획표와 블럭 배치를 유도하는 안내.
- **데이터 처리:** 없음.
- **최종 상태:** 즉시 블럭 배치가 가능한 상태.

### EC-13. 24시간 블럭 상태에서의 추가 배치 시도
- **발생 조건:** `durationMinutes = 1440` 블럭이 존재하는 날짜에 다른 블럭을 드롭함.
- **시스템 상태:** 가용 길이가 0이므로 배치 거부.
- **사용자 표시:** EC-06과 동일한 드롭 불가 표시.
- **데이터 처리:** 변경 없음.
- **최종 상태:** 기존 24시간 블럭이 유지된 상태.

## 9. Security & Permissions

### 9.1 Authentication
- 인증 체계가 존재하지 않는다. 로그인·회원가입 없이 앱 실행 즉시 모든 기능을 사용한다.

### 9.2 Authorization
- 사용자 유형 구분이 존재하지 않는다. 단말 사용자는 해당 단말의 모든 데이터에 대해 동일한 권한을 가진다.

### 9.3 Data Protection
- 수집·전송되는 개인정보가 없다.
- **로컬 전용 정책의 적용 범위 (확정):** 본 정책은 **앱이 능동적으로 수행하는 데이터 전송을 금지**하는 것이다. 구체적으로 앱은 사용자 데이터를 어떤 외부 서버·분석 도구·크래시 리포트에도 전송하지 않으며, 네트워크 전송 코드 경로를 갖지 않는다.
- **OS 기본 백업의 취급:** iOS의 iCloud 백업, Android의 Auto Backup 등 OS가 시스템 차원에서 수행하는 백업은 앱의 통제 범위 밖이며 본 정책의 금지 대상이 아니다. 이에 대한 명시적 차단(백업 제외 플래그 설정 등)은 이번 개발 범위에서 수행하지 않는다.
- 외부 전송 경로가 없으므로 전송 구간 암호화 요구사항이 발생하지 않는다.

### 9.4 Security Rules
- 요청하는 OS 권한은 아래로 한정한다.

| 권한 | 플랫폼 / 적용 범위 | 목적 | 미부여 시 동작 |
|------|-------------------|------|----------------|
| 알림 권한 | iOS 15+, Android 13(API 33)+ | 계획 알림 발송 | 알림 미발송, 배너 고지 (EC-01) |
| 정확 알람 권한 | Android 12(API 31)+ | 정시 알림 발송 | 부정확 알람으로 계속 발송, 지연 가능 (EC-02) |

- **정확 알람 권한의 위상:** 정확 알람 권한은 **정시성을 높이는 수단이며 알림 기능의 전제 조건이 아니다.** 미부여 상태에서도 알림 기능은 부정확 알람으로 제공된다. 따라서 이 권한을 정시 알림의 절대적 보장 수단으로 삼지 않는다.
- Android 12 미만에서는 정확 알람 권한 요청이 발생하지 않으며, 알림 권한은 Android 13 미만에서 런타임 요청 없이 부여된 것으로 취급한다.
- 위 목적 외의 OS 권한(위치, 연락처, 저장소 접근, 배터리 최적화 예외 등)을 요청하지 않는다.

## 10. Non-Functional Requirements

### NFR-01. 조작 반응성 (Performance)
- **기준 기기:** 최소 지원 OS 버전(iOS 15 / Android 8.0)을 만족하는 기기 중, 출시 후 5년 이내 보급형 기기를 성능 판정 기준으로 한다.
- 원형 계획표 드래그 중 렌더링 프레임률은 **평균 55fps 이상, 최저 30fps 이상**을 유지해야 한다.
- 터치 입력부터 화면 반영까지의 지연은 **100ms 이하**여야 한다.
- 드래그 중 겹침 경고 표시 반영 지연은 **100ms 이하**여야 한다.

### NFR-02. 캘린더 렌더링 성능 (Performance)
- 기준 기기에서 월간 캘린더의 월 이동 및 스크롤 시 프레임률은 **평균 55fps 이상**을 유지해야 한다.
- 이를 위해 날짜 셀에는 원형 미니 프리뷰를 렌더링하지 않고 도트 마커만 사용한다(OS-08).

### NFR-03. 알림 신뢰성 (Reliability)
- **보장 범위는 BR-07을 따른다.** 아래를 각각 구분하여 판정한다.
  - **유실(실패):** 예약이 완료된 알림이 권한·OS 정책 문제 없이 미발송되는 경우, 또는 갱신 트리거 발생 시 예약 가능한 후보가 예약되지 않는 경우.
  - **미예약(정상):** 예약 지평 초과로 인해 당장 예약되지 않은 상태. 이는 유실이 아니며 다음 갱신 시 예약된다.
- 갱신 트리거(T1~T4) 발생 시, 예약 가능한 후보가 예약 상한 내에서 전부 예약되어야 한다.
- 삭제·변경된 블럭의 알림은 다음 갱신 시점에 반드시 취소되어야 한다.

### NFR-04. 데이터 무결성 (Reliability)
- 저장·삭제·복사는 각각 원자적으로 처리되어, 실패 시 부분 반영 상태가 남지 않아야 한다(BR-12).
- 저장된 데이터에는 어떤 경우에도 아래가 존재해서는 안 된다.
  - 동일 `date` 내 겹치는 인스턴스 쌍
  - 10분의 배수가 아닌 `startMinute` 또는 `durationMinutes`
  - `startMinute + durationMinutes > 1440`인 인스턴스
  - `isLinkStart = true` 인스턴스가 0개이거나 2개 이상인 링크 그룹
- 모든 인스턴스가 자기 날짜 내에 완결되므로(`startMinute + durationMinutes ≤ 1440`), **날짜별 구간 검증만으로 링크 블럭을 포함한 전체 겹침 검증이 완전하다.**

### NFR-05. 오프라인 가용성 (Availability)
- 네트워크 연결이 전혀 없는 상태에서 모든 기능이 정상 동작해야 한다.

### NFR-06. 접근성 (Compatibility)
- 블럭은 색상과 아이콘을 동시에 제공하여, 색상만으로 구분이 어려운 사용자도 식별할 수 있어야 한다.
- 모든 블럭의 터치 영역은 최소 44dp / 44pt 이상을 확보해야 한다(BR-10).

### NFR-07. 플랫폼 호환성 (Compatibility)
- iOS와 Android 양 플랫폼에서 동일한 **계획 데이터 규칙과 편집 동작**이 적용되어야 한다.
- **알림 동작은 플랫폼별 차이를 허용한다.** 정확 알람 권한(Android 전용), 알림 권한 런타임 요청 시점, OS 절전 정책의 영향은 플랫폼별로 다르게 나타날 수 있으며, 이는 12.1의 기술 제약으로 반영된다.

**Android**

### 11.4 CI / Deployment Requirements

### 11.5 Credential Security Rule

## 12. Technical Constraints & Approved Technical Decisions

### 12.1 Technical Constraints

**플랫폼 및 저장소**
- 대상 플랫폼: iOS 15.0 이상 / Android 8.0(API 26) 이상.
- 서버 및 네트워크 통신을 사용하지 않는다.
- 데이터 저장은 로컬 SQLite로 한정한다.

**알림 관련 제약 (플랫폼 차이 명시)**
- 알림은 OS 로컬 알림 기능으로만 구현한다. 푸시 서버를 사용하지 않는다.
- **앱은 임의 시점에 자동 실행되지 않는다**(PP-02). 따라서 예약 큐 갱신은 앱 실행 시점(T1~T4)에만 가능하며, 백그라운드 페치나 상시 백그라운드 실행에 의존하는 설계는 금지한다(OS-10).
- **대기 알림 개수:** iOS는 앱당 대기 로컬 알림 개수에 OS 상한이 존재하고, Android는 개수 상한보다 정확 알람 사용 자체에 제약이 있다. 양 플랫폼 공통으로 안전한 상한으로 **50개**를 앱 자체 상한으로 고정한다.
- **정시성:** Android 12+ 에서 정확 알람 권한이 없으면 지연될 수 있고, 양 플랫폼 모두 절전 정책의 영향을 받을 수 있다. 이는 앱이 제거할 수 없는 제약이며 BR-07의 보장 범위에 반영된다.
- **재부팅:** Android는 재부팅 시 예약 알람이 소실되므로 부팅 완료 시점의 재생성 경로가 필요하다(11.3).

### 12.3 Implementation Freedom

**(1) 자유 영역**

## 13. Acceptance Criteria

### 13.1 Functional Acceptance
- FR-01 ~ FR-14의 모든 Acceptance Criteria가 충족된다.
- BR-01 ~ BR-13의 모든 규칙이 위배되지 않는다.
- EC-01 ~ EC-13의 모든 예외 상황이 정의된 최종 상태에 도달한다.
- 아래 항목은 **각각 관찰 가능한 결과가 확정되어 있으므로 개별 판정 대상**이다.
  - 자정 경계를 넘는 시작 핸들·종료 핸들·몸통 드래그의 결과값 (FR-07)
  - 날짜 복사 시 대표 인스턴스 기준 복사 및 T+1일 충돌 제외 (FR-13)
  - 완료 체크의 즉시 커밋 및 `Dirty` 미포함 (FR-14)
  - 갱신 트리거별 예약 큐 재계산 결과 (FR-11)

### 13.2 System Acceptance
- 캘린더 진입 → 날짜 선택 → 블럭 배치 → 드래그 조정 → 저장 → 캘린더 복귀의 전체 흐름이 중단 없이 완결된다.
- **저장 → 알림 예약 → 알림 발송의 연쇄가, 예약 지평 내의 알림에 한하여 앱 종료 상태에서 성립한다.** 예약 지평을 초과한 알림의 미발송은 EC-04에 따른 정상 동작이며 실패로 판정하지 않는다.
- 자정 교차 논리 블럭이 배치·저장·양일 표시·단일 알림·복사·완료 체크의 전 과정에서 정합성을 유지한다.
- 네트워크가 완전히 차단된 상태에서 위 전 항목이 동일하게 성립한다.
- **판정 조건의 전제:** 알림 관련 판정은 알림 권한이 부여된 단말에서 수행한다. 권한 미부여·정확 알람 미부여·OS 절전으로 인한 결과는 각각 EC-01, EC-02, PP-05에 따른 정상 동작으로 판정한다.

### 13.3 User Acceptance
- 앱 설치 직후, 별도 설정이나 계정 생성 없이 오늘의 하루 계획을 완성하고 저장할 수 있다.
- 블럭을 드래그해 원하는 시간대로 옮기고 길이를 조절하는 조작이 FR-07에 정의된 규칙대로 수행된다. 특히 아래가 사용자 시연으로 확인되어야 한다.
  - 23:00에 시작하는 8시간 수면 블럭을 자정을 넘겨 배치할 수 있다.
  - 그 블럭의 종료 핸들을 시계 방향으로 끌면 길어지고, 반시계 방향으로 끌면 짧아진다.
  - 그 블럭이 다음 날 계획표에도 이어져 표시된다.
- **알림 권한이 부여된 단말에서** 저장한 계획의 시각에 휴대폰 알림이 도달한다. 권한이 없는 경우 안내 배너를 통해 사용자가 원인과 해결 경로를 파악할 수 있다.
- 전날의 계획을 복사해 오늘의 계획을 즉시 완성할 수 있다.
- 계획을 실행한 뒤 완료 체크를 하면, 저장 버튼을 누르지 않고 나가도 캘린더에서 그날의 달성 정도를 확인할 수 있다.
