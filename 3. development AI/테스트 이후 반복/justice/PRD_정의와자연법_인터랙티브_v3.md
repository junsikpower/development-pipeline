# PRD — 「정의와 자연법」 인터랙티브 리딩 게임 (파일럿: 3장 규범 논리학) · v3

> 본 문서는 [P-4] 표준 명세서 생성 원칙에 따라, [P-1]의 APPROVED 항목만을 기준으로 작성되었습니다.

## 1. Project Overview

### 1.1 Project Definition

라이프니츠 『정의와 자연법』 독서 정리 노트(`justice_law.md`)를 **줄글 읽기가 아니라 논증 조작 행위로 체험하게 만드는 단일 파일 인터랙티브 웹 게임**이며, 그 첫 번째 파일럿으로 노트 3장(규범 논리학 — 대당 사각형)을 구현한다.

핵심 가치와 역할은 다음 네 가지다.

1. **가독성 전환**: 진입 장벽이 가장 높은 원문 구간을 조작 가능한 보드·카드로 바꾸어, 읽는 행위 자체를 플레이 행위로 전환한다.
2. **원전 방법론과의 동형성**: 라이프니츠의 방법(개념을 정의하고 → 연역으로 정리를 도출)을 게임 규칙(개념 카드를 합성하고 → 논리 관계로 판정)으로 그대로 구현한다.
3. **사유의 도구화**: 사용자가 노트에 남긴 의문점을 「미결 사건」으로 등록하고, 그에 대한 자기 결론을 「나의 정의론」 문서로 산출한다.
4. **해석 지위의 투명성**: 게임이 제시하는 모든 진술에 대해 그것이 원문의 진술인지, 해석인지, 게임이 채택한 형식 모델인지를 사용자가 구분할 수 있게 한다(BR-09).

### 1.2 Background

`justice_law.md`는 약 970행 분량의 독서 정리 노트이며, 세 가지 특징을 갖는다.

- **문제 상황**: 내용이 전부 줄글로 되어 있어 재독(再讀)이 극히 힘들다. 특히 양상 논리와 대당 사각형을 다루는 3장은 텍스트만으로는 관계 파악이 어렵다.
- **활용되지 않는 자산**: 노트 분량의 상당 부분이 사용자 본인의 의문점과 반박이다. 이는 요약이 아니라 논쟁 기록이며, 단순 요약 도구나 정답 맞히기 퀴즈로는 이 자산이 소실된다.
- **해석적 쟁점의 존재**: 3장의 핵심 도식은 양상 개념(가능·불가능·필연·우연)과 법 개념(허용·금지·의무·의무 아님)을 대응시킨다. 사용자는 이 대응 중 가능성과 우연성의 관계에 대해 명시적으로 이의를 제기했다(노트 151행). 따라서 이 프로젝트는 해당 대응을 **사용자에게 학습시키는 것**이 아니라 **사용자가 검증할 수 있게 하는 것**을 목표로 한다.

따라서 본 프로젝트는 요약 앱이 아니라, **원문을 안내하고 사용자의 논쟁을 이어가게 하는 도구**로 정의된다.

### 1.3 Target Environment

- **플랫폼**: 웹 브라우저. 지원 기준은 NFR-01에 정의한다.
- **실행 형태**: 외부 의존성 없이 브라우저에서 직접 열리는 **단일 HTML 파일**
- **실행 프로토콜**: `file://` 직접 실행을 기본 전제로 한다. 이 환경에서 브라우저별 보안 정책이 동일하지 않으므로, 본 명세는 특정 브라우저의 동작에 의존하지 않고 **다음 경계**를 규정한다.
  - **금지**: 제품이 스스로 개시하는 외부 리소스 취득(비동기 요청에 의한 데이터 로드). 실행에 필요한 데이터는 어떤 브라우저에서도 이 경로를 사용하지 않는다.
  - **허용**: 사용자의 명시적 파일 선택을 통한 로컬 파일 읽기, 그리고 사용자의 명시적 조작에 의한 파일 저장.
  - 자세한 규정은 BR-06에 둔다.
- **입력 방식**: 포인터(마우스/터치) 및 탭 기반 대체 입력
- **네트워크**: 실행에 네트워크 연결을 필수로 요구하지 않는다 (웹폰트 미로딩 시 시스템 폰트로 폴백)

## 2. Goals & Success Definition

### 2.1 Project Goals

- **G-1**: 노트 3장의 핵심 도식(대당 사각형의 네 항과 여섯 관계, 그리고 양상 개념과 법 개념의 대응)을 조작을 통해 이해하게 한다. 이때 원문의 진술과 게임이 채택한 형식 모델을 구분하여 제시한다(BR-09).
- **G-2**: 사용자의 의문 「가능성과 우연성은 사실상 논리적 동치 아닌가?」(노트 151행)를 **주장으로 반박하지 않고 조작 결과로 확인**할 수 있는 환경을 제공한다.
- **G-3**: 게임화 과정에서 원전이 왜곡되지 않도록, 모든 게임 콘텐츠가 원문 근거(`src`)와 주장 등급(`claimType`)에 결박되게 한다.
- **G-4**: 나머지 7개 챕터를 엔진 코드 재작성 없이 추가할 수 있는 확장 구조를 확보한다.
- **G-5**: 사용자의 미결 의문에 대한 자기 결론을 외부로 반출 가능한 문서로 산출한다.

### 2.2 Goal Completion State

| 목표 | 달성 시 시스템 상태 | 달성 시 사용자 상태 |
|---|---|---|
| G-1 | 보드 퍼즐이 BR-08의 판정 모델로 배치를 판정하고, 각 진술의 `claimType`이 UI에 구분 표시됨 | 네 항과 여섯 관계를 배치 경험으로 설명할 수 있고, 어떤 진술이 원문이고 어떤 것이 게임의 모델인지 구분할 수 있음 |
| G-2 | Sandbox에서 네 항을 자유 설정하면 16가지 조합 중 정합한 3가지와 위반 13가지가 구분 표시되고, I·O가 취할 수 있는 조합이 명시됨 | 자신의 의문을 조작 결과에 근거해 서술할 수 있음. 구체적으로 I와 O가 동치가 아니라는 사실과, 그럼에도 동치처럼 보이는 이유를 각각 구분해 진술할 수 있음 |
| G-3 | 모든 콘텐츠 엔티티가 `src`와 `claimType`을 보유하고, 어느 화면에서든 원문 보기가 가능함 | 게임 내 진술을 원문과 대조하고, 원문에 없는 해석적 등식을 게임의 사실로 오인하지 않음 |
| G-4 | 엔진 코드와 챕터 콘텐츠 데이터가 분리되어, 챕터 추가가 데이터 추가만으로 가능함 | 후속 챕터 제작을 글쓰기 작업으로 수행할 수 있음 |
| G-5 | 「나의 정의론」이 정의된 구조의 Markdown으로 내보내짐 | 산출된 문서를 원래 노트에 병합할 수 있음 |

**G-1과 G-2의 관계 (필수 명시)**: 두 목표는 충돌하지 않고 선후 관계에 있다. G-2의 검증이 성립하려면 검증 대상이 되는 형식 모델이 먼저 고정되어야 한다. 모델이 없으면 "동치인가"라는 질문 자체가 판정 불가능하기 때문이다. 따라서 게임은 ① 노트 도식을 형식 모델로 고정하고(G-1), ② 그 모델 안에서 I와 O의 관계가 실제로 어떻게 되는지를 사용자가 직접 조작해 확인하게 하며(G-2), ③ 그 모델이 원문의 사실이 아니라 게임이 채택한 형식화임을 `claimType`으로 표시한다(G-3). 게임은 모델의 참을 주장하지 않고, 모델의 귀결만을 계산한다(BR-02).

### 2.3 Overall Success Conditions

1. 3장 파일럿을 6단계 흐름(진입 → 리딩 → 보드 퍼즐 → 반례 배틀 → 미결 사건 → 결산)으로 처음부터 끝까지 완주할 수 있다.
2. 승인된 7종 메커니즘 중 5종(정의 합성, 반례 배틀, 대당 사각형 퍼즐, 내 의문 노트, 개념 지도)이 실제로 동작한다.
3. **보드 판정, Sandbox, 전수 검사가 모두 동일한 판정 함수를 사용**하며, 네 항의 참/거짓 조합 전수(16가지)에 대해 BR-04의 규칙과 일치한다. 구체적으로 정합한 벡터가 정확히 3가지(의무·금지·자유)로 산출된다.
4. 챕터 콘텐츠 데이터 블록을 추가·교체하는 것만으로 다른 챕터 구성이 로드되며, 엔진 코드 수정이 요구되지 않는다.
5. 「나의 정의론」 Markdown이 FR-09에 정의된 구조로 산출된다.
6. 모든 콘텐츠가 자기 검사(BR-10)를 통과한다.

## 4. Functional Requirements

### FR-01. 챕터 진입 및 리딩 뷰

**Purpose / Rationale**
읽기를 제거하지 않고, 읽어야만 카드를 얻고 카드가 있어야 진행이 가능한 구조를 만들기 위함이다. 6단계 흐름의 1~2단계에 해당한다.

**Trigger**
사용자가 홈(서재)에서 3장을 선택한다.

**Input**
챕터 콘텐츠 데이터의 리딩 카드 목록(`ReadingCard[]`), 개념 카드 정의(`Concept[]`), 획득 지점이 `reading_complete`로 지정된 반례 카드 목록.

**Processing / Business Rules**
- 진입 시 챕터 질문 "좋은 사람(Vir Bonus)에게 가능한 것과 해야만 하는 것은 같은가?"를 제시한다.
- 노트 본문을 리딩 카드 단위로 순차 제시한다.
- **리딩 카드의 "소비" 정의**: 한 리딩 카드는 사용자가 해당 카드에 대해 **명시적 진행 조작(다음으로 넘기기)을 수행한 시점**에 소비된 것으로 판정한다. 체류 시간, 스크롤 위치, 가시성은 판정 기준으로 사용하지 않는다. 마지막 카드는 진행 조작 대신 완료 조작으로 소비된다.
- 이미 소비한 카드로 되돌아가 다시 볼 수 있으며, 되돌아가는 행위는 소비 상태를 해제하지 않는다.
- 본문 내 핵심 용어는 인터랙티브 토큰으로 표시하며, 선택 시 해당 개념의 정의와 `claimType` 배지를 팝업으로 보여준다.
- 모든 리딩 카드가 소비되면 개념 카드(양상 개념 ↔ 법 개념 대응 4종)를 획득한다.
- 동시에, 획득 지점이 `reading_complete`로 지정된 반례 카드를 획득한다(BR-07).
- 획득 완료 시에만 다음 단계(보드 퍼즐) 진입 수단을 활성화한다.

**Output**
획득한 개념 카드, 획득한 반례 카드, 다음 단계 진입 수단.

**Expected State**
진행 상태에 챕터 3의 리딩 단계 완료, 개념 카드 보유, 해당 반례 카드 보유가 기록된다.

**Acceptance Criteria**
- 모든 리딩 카드에 진행 조작을 수행하면 개념 카드가 덱에 표시된다.
- 진행 조작 없이 스크롤만으로는 카드가 소비되지 않는다.
- `reading_complete` 지점의 반례 카드가 덱에 표시된다.
- 리딩을 완료하지 않은 상태에서는 보드 퍼즐에 진입할 수 없다.
- 용어 토큰 선택 시 정의와 `claimType` 배지가 표시된다.

### FR-02. 개념 카드 획득 및 정의 합성

**Purpose / Rationale**
라이프니츠의 연역 연쇄(개념이 개념을 낳는 구조)를 카드 합성으로 체험하게 하기 위함이다.

**Trigger**
사용자가 덱에서 둘 이상의 개념 카드를 선택해 합성을 시도한다.

**Input**
보유 개념 카드 집합, 각 개념의 `derivedFrom` 속성.

**Processing / Business Rules**
- 합성 가능 여부는 별도 레시피 테이블이 아니라 대상 개념의 `derivedFrom` 배열 충족 여부로 판정한다.
- `derivedFrom`의 모든 구성 개념을 보유한 경우에만 파생 개념이 획득된다.
- 합성 성공 시 새 개념 카드가 덱과 개념 지도에 추가된다.
- **콘텐츠 계약**: 파일럿 챕터의 콘텐츠 데이터는 `derivedFrom`이 비어 있지 않은 개념을 **최소 1개 이상** 포함해야 하며, 그 구성 개념이 모두 같은 챕터 안에서 획득 가능해야 한다. 이 조건을 만족하지 않는 콘텐츠는 검증에서 실패로 처리한다(BR-10). 어떤 개념이 어떤 개념에서 파생되는지의 실제 값은 콘텐츠 데이터에서 확정하며, Development AI가 생성하지 않는다.

**Output**
파생 개념 카드, 합성 성공/실패 피드백(실패 시 부족한 구성 개념 목록).

**Expected State**
덱과 개념 지도가 갱신된다.

**Acceptance Criteria**
- 구성 개념을 모두 보유하면 합성이 성공한다.
- 하나라도 미보유 시 합성이 성공하지 않으며, 부족한 구성 요소를 확인할 수 있다.
- 콘텐츠에 합성 가능한 개념이 최소 1개 존재한다.

### FR-03. 대당 사각형 보드 퍼즐 (3단계)

**Purpose / Rationale**
3장의 핵심 도식을 텍스트가 아니라 조작 대상으로 만든다. 파일럿의 최우선 기능이다.

**Trigger**
FR-01 완료 후 사용자가 보드 퍼즐에 진입한다.

**Input**
단계 정의(`BoardStage[]`: 활성 관계 집합, 소속 행위 사례 목록), 행위 사례 카드(`BoardItem[]`: 진리값 벡터 `truth`, 근거 `rationale`, `src`, `claimType`).

**Processing / Business Rules**

- 보드는 네 사분면으로 구성한다. 각 항의 표기는 다음과 같으며, 양상 표기는 `model` 등급, 법 개념 대응은 `source` 등급이다(BR-09).

| 항 | 전통 표기 | 양상 표기(model) | 노트의 법 개념 대응(source, 노트 127~135행) |
|---|---|---|---|
| A | 전칭긍정 | □φ (필연) | 의무 |
| E | 전칭부정 | □¬φ (불가능) | 부정의한 것 · 금지 |
| I | 특칭긍정 | ◇φ (가능) | 정의로운 것 · 허용 |
| O | 특칭부정 | ◇¬φ (우연) | 의무가 아닌 것 · 자유 |

- **판정 모델은 BR-08을 따른다.** 사분면은 진리값을 갖지 않으며, 진리값은 각 행위 사례 카드에 귀속된다.
- 사용자는 행위 사례 카드를 사분면에 배치한다. 배치된 카드는 다른 사분면으로 이동할 수 있으며, 시도 횟수에 제한을 두지 않는다.
- 한 사분면에 복수의 카드가 놓일 수 있다.
- **단계별 난이도는 판정에 활성화되는 관계의 수로 상승한다.**

| 단계 | 활성 관계 | 학습 목표 | 소재 |
|---|---|---|---|
| 1단계 | 모순 2개 (A–O, E–I) | 네 항의 대응 확인. 필연↔우연, 불가능↔가능이 서로를 배제한다는 관계 파악 | 3장의 개념 정의 |
| 2단계 | 1단계 + 반대(A–E), 소반대(I–O) | 상단 두 항은 함께 참일 수 없고 하단 두 항은 함께 거짓일 수 없다는 비대칭 파악 | 3장의 양상 개념 사례 |
| 3단계 | 여섯 관계 전부 (함축 A→I, E→O 추가) | 의무가 허용을 함축한다는 상하 관계 파악 | 체스 비유(퀸의 대각선 이동=허용 / 체크메이트 회피=의무, 노트 147~148행) |

- 각 단계의 클리어 조건은 다음 두 가지를 동시에 만족하는 것이다. ① 해당 단계의 모든 행위 사례 카드가 사분면에 배치되었을 것. ② 배치된 모든 카드가 BR-08의 정합 판정을 통과했을 것.
- 미배치 카드가 하나라도 존재하면 단계는 성립하지 않는다(EC-09).
- **관계선 표시 규칙**: 관계선은 항상 **하나의 기준 카드**의 진리값 벡터에 대해 평가한다. 기준 카드는 사용자가 마지막으로 선택하거나 배치한 카드이며, 기준 카드가 없으면 관계선은 중립 상태로 표시하고 판정하지 않는다. 기준 카드는 UI에서 명시적으로 표시된다.
- 비활성 관계선은 표시하되 판정 대상에서 제외하며, 활성 관계와 시각적으로 구분한다(색상 외 수단 포함, FR-11).
- 각 단계 성립 시, 획득 지점이 해당 단계로 지정된 반례 카드를 획득한다(BR-07).
- 판정 문구는 BR-02를 따른다.
- 단계 수는 콘텐츠 데이터의 `stages` 배열 길이로 결정되며, 엔진에 3이 고정되지 않는다. 파일럿 콘텐츠가 3단계를 사용하는 것이다.

**Output**
관계선 시각화, 카드별 정합/위반 판정과 그 사유, 단계 성립 여부, 단계별 획득 반례 카드.

**Expected State**
3단계 완료가 진행 상태에 기록되고 다음 단계(반례 배틀)가 활성화된다. 배틀에 필요한 반례 카드가 전량 확보된 상태가 된다.

**Acceptance Criteria**
- 카드를 사분면에 배치·이동할 수 있으며 재배치 횟수에 제한이 없다.
- 한 사분면에 복수 카드를 배치해도 판정이 각 카드에 대해 독립적으로 수행된다.
- 기준 카드가 UI에 명시되고, 관계선이 기준 카드의 벡터에 대해 평가된다.
- 각 단계에서 활성 관계만 판정 대상이 되고, 비활성 관계와 시각적으로 구분된다.
- 모든 카드가 배치되고 모두 정합일 때만 단계가 성립한다.
- 1 → 2 → 3단계로 진행하면서 활성 관계 수가 2 → 4 → 6으로 증가한다.
- 단계 수가 콘텐츠 데이터로 결정된다.

### FR-04. Sandbox 모드

**Purpose / Rationale**
사용자의 의문 「가능성과 우연성은 논리적 동치 아닌가?」를 주장에 대한 설명이 아니라 조작 결과로 확인하게 하기 위함이다. 「내 의문 노트」를 핵심 축으로 삼은 결정에 직접 봉사한다.

**Trigger**
사용자가 보드 화면 또는 미결 사건 화면에서 Sandbox 모드를 실행한다.

**Input**
가상 행위 φ*에 대한 A·E·I·O 네 항 각각의 참/거짓 설정값(BR-08의 진리값 벡터와 동일한 자료형).

**Processing / Business Rules**
- 정답 판정을 하지 않는다. 사용자가 네 항의 참/거짓을 자유롭게 설정한다.
- 여섯 관계 전부를 항상 활성 상태로 평가한다(FR-03의 단계별 활성화는 Sandbox에 적용하지 않는다).
- 판정은 BR-08의 동일한 순수 함수를 사용한다.
- 모순된 조합도 차단하지 않고 허용한다(EC-07).
- **출력 규칙**은 다음 네 가지를 모두 포함한다.
  1. **관계별 결과**: 여섯 관계 각각에 대해 성립/위반과 그 조건문.
  2. **벡터의 해석**: 설정한 벡터가 정합인 경우, 그것이 대응하는 법 개념 상태를 표시한다. 정합 벡터는 다음 셋뿐이다.
     - ⟨A=T, E=F, I=T, O=F⟩ → **의무**
     - ⟨A=F, E=T, I=F, O=T⟩ → **금지(부정의한 것)**
     - ⟨A=F, E=F, I=T, O=T⟩ → **자유(허용이면서 의무가 아님)**
     위반인 경우 "이 조합을 만족하는 행위는 존재할 수 없음"과 위반된 관계를 표시한다.
  3. **I·O 전용 대조표**: I와 O를 독립 토글로 제공하고, 네 조합 각각의 귀결을 상시 표시한다.

     | I(가능) | O(우연) | 귀결 |
     |---|---|---|
     | T | F | 의무 (A=T, E=F) |
     | F | T | 금지 (A=F, E=T) |
     | T | T | 자유 (A=F, E=F) |
     | F | F | **성립 불가** — 소반대 관계 위반 |
  4. **의문에 대한 대조 진술**: 위 표로부터 도출되는 두 사실을 병기한다. ① I=T이면서 O=F인 정합 벡터(의무)가 존재하므로 **I와 O는 동치가 아니다**. ② 그럼에도 정합 벡터 셋 중 하나(자유)에서는 I와 O가 함께 참이므로, 자유에 해당하는 행위만 놓고 보면 동치처럼 보인다. 이 진술은 BR-02에 따라 "정답"이 아니라 "채택된 형식 모델에서의 귀결"로 표기하며, 모델 자체는 `model` 등급임을 함께 표시한다(BR-09).

**Output**
관계별 성립/위반 상태, 벡터 해석, I·O 대조표, 의문에 대한 대조 진술.

**Expected State**
Sandbox 조작 결과를 미결 사건 서술에 참조할 수 있는 상태가 된다. Sandbox 진입 및 종료는 보드의 카드 배치 상태를 변경하지 않는다.

**Acceptance Criteria**
- 네 항의 참/거짓을 임의로 설정할 수 있다.
- 어떤 설정에서도 여섯 관계 각각의 성립/위반이 표시된다.
- 정합 벡터 3가지에 대해 각각 의무·금지·자유가 표시된다.
- I·O 네 조합의 귀결표가 표시되며, (F,F)가 성립 불가로 표시된다.
- 논리적으로 모순인 설정이 차단되지 않고 위반 표시로 처리된다.
- Sandbox를 종료하면 보드의 배치 상태가 진입 전과 동일하다.

### FR-05. 반례 배틀

**Purpose / Rationale**
통합안(A 컨셉)의 서사형 메커니즘을 파일럿에서 함께 검증하기 위함이며, 6단계 흐름의 4단계에 해당한다.

**Trigger**
FR-03 완료 후 배틀에 진입한다.

**Input**
상대 명제(`Proposition`)와 그 명제를 지지하는 전제 목록(`Premise[]`), 사용자가 FR-01 및 FR-03에서 획득한 반례 카드(`Counterexample[]`).

**Processing / Business Rules**
- 명제는 체력 수치가 아니라 **전제 위에 선 구조물**로 표현한다.
- **"적중"의 정의**: 반례 카드의 `defeats` 값과 제출 대상 전제의 식별자가 **문자열로 일치**하는 경우를 적중으로 한다. 논리식 평가나 부분 일치는 사용하지 않는다.
- 적중 시 해당 전제가 `defeated`로 전이한다. 적중하지 않으면 전제는 변하지 않으며, 카드도 소모되지 않는다.
- 명제를 지지하는 전제가 **모두** `defeated`가 되면 명제가 `collapsed`로 전이한다.
- 각 반례 카드는 `explain`(해당 전제를 왜 무너뜨리는지)을 필수로 가지며, 적중 시 표시된다.
- 파일럿의 배틀 소재는 **노트 원문 170행에 기록된 사용자 본인의 의문**이다. 해당 원문은 라이프니츠의 결론(노트 168행: "그런 행위를 의무로 그가 여기는 이유는 '모든 사람을 사랑하는 사람이' 그렇게 행동하는 것이 가능하기 때문이다")에 대해 "트롤리 딜레마처럼 모두를 살릴 가능성이 없다고 여겨지는 상황에서 (…) 불가능하다 해서 의무가 아니게 되는가?"라고 반문한다. 따라서 대상 명제와 트롤리 딜레마 소재는 모두 `src`(170행)를 가지며 BR-01을 충족한다.
- 배틀에 사용되는 모든 명제·전제·반례는 BR-01에 따라 `src`와 `claimType`을 보유해야 한다.
- 판정 문구는 BR-02를 따른다.

**Output**
전제 붕괴 및 명제 붕괴 연출, 적중한 반례의 `explain` 텍스트.

**Expected State**
배틀 완료가 진행 상태에 기록되고 미결 사건 단계가 활성화된다.

**Acceptance Criteria**
- 배틀 진입 시점에 필요한 반례 카드를 모두 보유한 상태다.
- 반례 카드를 전제에 대응시켜 제출할 수 있다.
- `defeats`와 전제 식별자가 일치하는 반례만 전제를 무너뜨린다.
- 불일치 시 전제가 변하지 않고 카드도 소모되지 않는다.
- 지지 전제가 모두 무너지면 명제가 붕괴 상태로 전이한다.
- 배틀에 등장하는 모든 명제·전제·반례에서 원문 보기가 동작한다.

### FR-06. 내 의문 노트 (미결 사건)

**Purpose / Rationale**
게임의 핵심 축이다. 사용자가 노트에 남긴 의문을 소비 대상이 아니라 작업 대상으로 만든다.

**Trigger**
FR-05 완료 시 미결 사건 #1 「가능성과 우연성은 동치인가」(노트 151행)가 개시된다.

**Input**
의문 원문 인용, 변호 논거 카드(`Argument[]`, `side: "defense"`), 반박 논거 카드(`Argument[]`, `side: "objection"`), 사용자 서술 텍스트.

**Processing / Business Rules**
- 사건은 `open`(미결) 또는 `resolved`(정리됨) 상태를 가진다.
- 사용자는 변호 논거와 반박 논거를 자유롭게 선택·해제할 수 있다. 어느 한쪽만 선택해도 되고 양쪽을 함께 선택해도 된다.
- 사용자는 자유 서술로 자기 결론을 작성한다. 이 서술이 「나의 정의론」의 본문이 된다.
- **`resolved` 전이 조건**은 다음 두 가지를 모두 만족하는 것이다.
  1. 논거 카드를 **최소 1장 이상** 선택했을 것. (근거: 이 사건은 논거 조립을 작업 대상으로 삼는 기능이므로, 논거를 전혀 참조하지 않은 상태는 이 기능이 정의하는 작업이 수행되지 않은 상태다.)
  2. 사용자 서술이 **공백을 제외하고 20자 이상**일 것. (근거: "비어 있지 않을 것"만으로는 한 글자 입력으로 최종 게이팅이 통과되어 산출물이 성립하지 않는다. 20자는 한 문장의 최소 길이에 해당하는 하한이며, 상한이나 내용 검사는 두지 않는다.)
- Sandbox 조작 이력은 전이 조건에 포함하지 않는다. Sandbox는 게이팅 대상이 아니기 때문이다(BR-05).
- 전이 조건 미충족 시, 어떤 조건이 미충족인지 구분해 표시한다.
- 각 논거 카드는 `src`와 `claimType`을 가지며 원문 보기와 연결된다.

**Output**
조립된 논거 구성, 저장된 사용자 서술, 사건 상태.

**Expected State**
사건이 `resolved`로 전이하고 결산 단계가 활성화된다.

**Acceptance Criteria**
- 의문 원문과 양측 논거가 표시된다.
- 사용자 서술이 입력·보존된다.
- 논거 미선택 또는 서술 20자 미만인 상태에서는 `resolved`로 전이하지 않으며, 미충족 조건이 구분되어 표시된다.
- 두 조건을 모두 만족하면 전이한다.

### FR-07. 원문 보기 및 주장 등급 표시

**Purpose / Rationale**
게임이 원문을 대체하지 않고 안내하도록 하며, 게임화로 인한 원전 왜곡을 구조적으로 차단한다.

**Trigger**
사용자가 임의의 화면에서 콘텐츠 요소의 원문 보기를 실행한다.

**Input**
해당 요소의 `src`(원문 라인 범위)와 `claimType`.

**Processing / Business Rules**
- 모든 콘텐츠 엔티티는 `src`와 `claimType`을 보유한다(BR-01, BR-09).
- 원문 보기 실행 시 해당 라인 범위의 노트 원문을 표시한다.
- 함께 `claimType` 배지를 표시한다. 배지는 `source` / `interpretation` / `model` 세 종류이며, 각각의 의미를 사용자가 확인할 수 있어야 한다.
- `claimType`이 `model`인 요소는 원문에 그 형식화가 문자 그대로 존재하지 않을 수 있으므로, `src`는 **그 모델이 근거한 원문 구간**을 가리키며 그 사실을 함께 표시한다.
- 원문 텍스트는 콘텐츠 데이터와 함께 제품에 내장되며, 표시를 위해 외부 파일 접근이나 비동기 요청을 수행하지 않는다(BR-06).
- 원문 보기는 현재 진행 중인 플레이 상태를 초기화하지 않는다.

**Output**
해당 원문 구간과 `claimType` 배지.

**Expected State**
진행 상태 변화 없음.

**Acceptance Criteria**
- 어느 화면에서든 원문 보기가 가능하다.
- 표시되는 원문이 해당 요소의 `src` 범위와 일치한다.
- 세 종류의 `claimType` 배지가 시각적으로 구분된다.
- `file://` 직접 실행 환경에서도 원문 보기가 동작한다.

### FR-08. 개념 지도 (Atlas)

**Purpose / Rationale**
진도를 수치가 아니라 지도의 완성도로 표현하여, 개념 간 연역 관계를 시각적으로 남긴다.

**Trigger**
사용자가 개념 지도를 연다. 또는 개념 획득·합성 시 자동 갱신된다.

**Input**
보유 개념 목록, 각 개념의 `derivedFrom`, 콘텐츠 데이터에 사전 지정된 노드 좌표(`pos`).

**Processing / Business Rules**
- 노드 배치는 물리 시뮬레이션이 아니라 **사전 지정 좌표**를 사용하여 항상 동일한 레이아웃으로 렌더링한다.
- 획득한 개념은 점등 상태, 미획득 개념은 실루엣 상태로 표시한다.
- `derivedFrom` 관계를 연결선으로 그린다.

**Output**
개념 그래프.

**Expected State**
진행 상태 변화 없음(표시 전용).

**Acceptance Criteria**
- 동일한 보유 상태에서 항상 동일한 좌표로 렌더링된다.
- 획득/미획득이 시각적으로 구분된다.

### FR-09. 결산 및 「나의 정의론」 내보내기

**Purpose / Rationale**
게임의 최종 산출물을 사용자의 원래 노트로 되돌리기 위함이다.

**Trigger**
FR-06 완료 후 결산 화면에서 내보내기를 실행한다.

**Input**
정리된 미결 사건의 사용자 서술, 선택된 논거 목록, 획득 개념 목록, 원문 근거, Sandbox 최종 설정값(존재하는 경우).

**Processing / Business Rules**
- Markdown 형식으로 문서를 생성한다.
- **출력 구조는 다음 순서로 고정한다.**
  1. 제목: `# 나의 정의론 — {챕터 제목}`
  2. `## 다룬 의문` — 의문 원문 인용(인용 블록) 및 `src` 라인 범위
  3. `## 나의 결론` — 사용자 서술 전문
  4. `## 참조한 논거` — 선택한 논거를 변호/반박으로 구분한 두 소제목 아래 목록. 각 항목은 논거 본문, `claimType`, `src` 라인 범위를 포함
  5. `## 조작 기록` — Sandbox 최종 설정값과 그 귀결(정합 여부 및 대응 상태). Sandbox를 사용하지 않았으면 이 절을 생략
  6. `## 획득한 개념` — 개념명(한국어·라틴어), 정의문, `src` 목록
  7. `---` 이후 생성 시각과 원문 버전 식별자(`sourceVersion`)
- 선택되지 않은 논거는 출력하지 않는다.
- 생성된 문서는 사용자가 파일로 저장할 수 있어야 한다.

**Output**
「나의 정의론」 Markdown 파일.

**Expected State**
챕터 3이 완료 상태로 기록된다.

**Acceptance Criteria**
- 결산 화면에서 Markdown을 내보낼 수 있다.
- 내보낸 문서가 위 6~7개 절을 정의된 순서로 포함한다.
- 선택하지 않은 논거가 포함되지 않는다.
- 각 논거와 개념에 `src` 라인 범위가 표기된다.

### FR-10. 진행 상태 저장 및 불러오기

**Purpose / Rationale**
브라우저 저장소를 사용할 수 없는 실행 환경에서도 사용자 서술이 소실되지 않게 한다.

**Trigger**
사용자가 내보내기 또는 불러오기를 실행한다. 또는 저장소 사용이 가능한 환경에서 상태가 변경된다.

**Input**
현재 진행 상태 객체(`GameState`), 또는 사용자가 파일 선택으로 지정한 JSON 파일.

**Processing / Business Rules**
- 진행 상태는 6.3에 정의된 `GameState` 스키마를 따르는 단일 객체로 메모리에서 유지한다.
- 내보낸 JSON은 최상위에 `schemaVersion`(정수)과 `sourceVersion`(문자열)을 포함한다.
- 불러오기는 비동기 외부 요청이 아니라 **사용자의 파일 선택을 통한 로컬 파일 읽기**로 수행한다(BR-06).
- **불러오기 검증 순서**: ① JSON 파싱 성공 여부 → ② `schemaVersion`이 제품이 지원하는 값인지 → ③ `sourceVersion`이 내장 원문의 것과 일치하는지 → ④ 필수 필드 존재 및 타입 일치 → ⑤ 참조 무결성(보유 개념·반례 식별자가 내장 콘텐츠에 존재하는지). 하나라도 실패하면 전체를 적용하지 않는다(EC-03).
- `schemaVersion`이 제품보다 낮은 경우: 파일럿에서는 마이그레이션을 수행하지 않고 불일치로 처리한다. 마이그레이션은 챕터 확장 시점의 과제로 이연한다.
- `sourceVersion` 불일치 시: 라인 근거가 다른 원문을 가리킬 수 있으므로 적용하지 않고 사유를 표시한다(BR-01).
- 브라우저 저장소를 사용할 수 있는 환경에서는 이를 보조 수단으로 사용하고, 사용할 수 없으면 내보내기/불러오기 방식으로 자동 폴백한다.
- 저장소 사용 가능 여부에 따라 기능이 실패하지 않아야 한다.

**Output**
상태 JSON 파일, 복원된 진행 상태, 또는 사유가 명시된 실패 결과.

**Expected State**
불러오기 성공 시 진행 상태가 저장 시점으로 복원된다. 실패 시 기존 상태가 그대로 유지된다.

**Acceptance Criteria**
- 저장소 사용 불가 환경에서도 게임이 정상 동작하며 내보내기로 상태를 보존할 수 있다.
- 내보낸 JSON을 불러오면 진행 상태가 복원된다.
- `schemaVersion` 또는 `sourceVersion`이 다른 파일은 적용되지 않고 사유가 표시된다.
- 검증 실패 시 부분 적용이 발생하지 않는다.
- `file://` 직접 실행 환경에서도 불러오기가 동작한다.

### FR-11. 대체 입력 및 접근성

**Purpose / Rationale**
포인터 드래그가 동작하지 않는 환경과 색각 이상 사용자, 모션 민감 사용자를 배제하지 않기 위함이다.

**Trigger**
보드 퍼즐 및 배틀에서 카드 배치·제출을 수행할 때.

**Input**
포인터 입력 또는 탭 입력, 사용자 시스템의 모션 감소 설정.

**Processing / Business Rules**
- 카드 배치는 포인터 기반 드래그와 **탭(카드 선택) → 탭(사분면 선택)** 두 경로를 모두 제공한다. 배틀의 반례 제출도 동일한 두 경로를 제공한다.
- 관계선은 색상만이 아니라 선 스타일로 구분한다(반대=실선, 소반대=파선, 모순=점선, 함축=화살표).
- 활성/비활성 관계선은 선 두께와 불투명도로 구분하며, 색상에만 의존하지 않는다.
- 정합/위반 상태는 색상 외에 아이콘 또는 텍스트 표기를 병행한다.
- 모션 감소 설정이 활성화된 경우 애니메이션을 축소한다.

**Output**
동일한 배치 결과.

**Expected State**
입력 방식과 무관하게 동일한 판정 결과에 도달한다.

**Acceptance Criteria**
- 드래그 없이 탭만으로 모든 배치와 제출을 완료할 수 있다.
- 흑백 환경에서도 네 종류의 관계선, 활성/비활성 상태, 정합/위반 상태가 구별된다.

## 5. Business / System Rules

### BR-01. 원문 근거 필수 규칙

모든 콘텐츠 엔티티(개념, 리딩 카드, 행위 사례, 명제, 전제, 반례, 논거, 의문)는 원문 라인 범위를 가리키는 `src` 속성을 필수로 가진다. `src`가 없는 콘텐츠는 유효한 콘텐츠로 취급하지 않는다.

**원문 버전 결박**: 라인 번호만으로는 원문이 변경되었을 때 다른 내용을 가리킬 수 있다. 따라서 콘텐츠 데이터는 최상위에 `sourceVersion`(내장 원문의 버전 식별자)과 `sourceHash`(내장 원문 전체의 해시)를 보유하며, 제품 기동 시 내장 원문으로부터 계산한 해시와 일치하는지 확인한다(BR-10). 진행 상태 파일에도 `sourceVersion`을 기록해 불러오기 시 대조한다(FR-10).

### BR-02. 판정 문구 규칙

보드 퍼즐과 반례 배틀, Sandbox의 판정은 "정답/오답"이 아니라 **"채택된 형식 모델에서의 귀결"**로 표기한다. 3장에는 사용자가 이미 이의를 제기한 해석적 쟁점이 존재하므로, 시스템이 해석의 최종 심판자로 표시되어서는 안 된다. 시스템은 모델의 참을 주장하지 않고 모델의 귀결만을 계산한다.

### BR-03. 엔진/콘텐츠 분리 규칙

게임 로직(엔진)과 챕터 콘텐츠는 **소스 수준에서 분리**한다. 엔진 코드는 특정 챕터의 내용을 알지 못하며, 챕터 고유의 내용은 전부 콘텐츠 데이터에 기술한다. 챕터 추가는 콘텐츠 데이터의 추가만으로 가능해야 하며 엔진 코드의 수정을 요구해서는 안 된다. 물리적 배포 형태(단일 HTML 내 인라인 데이터 블록)는 BR-06을 따르며, 이는 소스 수준 분리 원칙과 양립한다. 콘텐츠 데이터의 계약은 6.3에 정의한다.

### BR-04. 대당 사각형 관계 규칙 테이블

관계는 화면이나 개별 퍼즐에 하드코딩하지 않고, 선언적 규칙 테이블로 정의하며 판정은 순수 함수로 수행한다. 규칙은 다음 여섯 가지이며, 모두 **하나의 행위에 대한 네 항의 진리값 벡터**에 적용된다(BR-08).

| 식별자 | 관계 | 대상 | 성립 조건 |
|---|---|---|---|
| `contrary_AE` | 반대 | A–E | ¬(A ∧ E) |
| `subcontrary_IO` | 소반대 | I–O | I ∨ O |
| `contradictory_AO` | 모순 | A–O | A ≠ O |
| `contradictory_EI` | 모순 | E–I | E ≠ I |
| `subalternation_AI` | 함축 | A→I | ¬A ∨ I |
| `subalternation_EO` | 함축 | E→O | ¬E ∨ O |

퍼즐 단계별 활성 관계 집합(FR-03)은 이 테이블의 부분집합으로 콘텐츠 데이터에 식별자로 선언하며, 판정 함수는 활성 집합을 인자로 받아 동작한다. 규칙 자체를 단계별로 중복 정의하지 않는다.

**전수 귀결(고정 사실)**: 여섯 관계를 모두 적용할 때, 16가지 진리값 조합 중 정합한 것은 정확히 3가지다 — ⟨T,F,T,F⟩(의무), ⟨F,T,F,T⟩(금지), ⟨F,F,T,T⟩(자유). 이 결과는 판정 함수의 검증 기준이며(13.2), Sandbox의 출력 근거다(FR-04).

### BR-05. 진행 게이팅 규칙

6단계 플레이 흐름은 순차 진행을 원칙으로 한다. 각 단계는 직전 단계의 완료를 활성화 조건으로 가진다. 단, 원문 보기(FR-07), 개념 지도(FR-08), Sandbox 모드(FR-04)는 게이팅 대상이 아니며 언제든 접근 가능하고, 게이팅 조건에도 포함되지 않는다.

### BR-06. 로컬 실행 및 리소스 결합 규칙

산출물은 `file://` 프로토콜로 직접 열리는 것을 기본 실행 방식으로 한다. 브라우저별 보안 정책이 동일하지 않으므로, 특정 브라우저의 동작에 의존하지 않도록 다음을 규정한다.

1. 챕터 콘텐츠 데이터와 원문 텍스트는 **단일 HTML 문서 내부의 인라인 데이터 블록**으로 포함하며, 엔진은 이 블록을 데이터로 읽는다.
2. **제품이 스스로 개시하는 외부 리소스 취득을 실행 경로에서 사용하지 않는다.** 실행에 필요한 어떤 데이터도 이 경로로 얻지 않는다.
3. 챕터 추가·교체는 인라인 데이터 블록의 추가·교체로 수행하며, 이는 BR-03의 분리 원칙을 위배하지 않는다.
4. **사용자의 명시적 조작에 의한 로컬 파일 읽기 및 파일 저장은 허용한다.** 파일럿에서 이에 해당하는 기능은 진행 상태 불러오기·내보내기(FR-10)와 「나의 정의론」 내보내기(FR-09)뿐이다. 외부 콘텐츠 JSON 로드는 파일럿 범위에서 제외한다(3.2).
5. 웹폰트는 실행 필수 리소스가 아니며, 취득 실패 시 시스템 폰트로 폴백한다(EC-06).

### BR-07. 반례 카드 획득 경로 규칙

모든 반례 카드는 콘텐츠 데이터에 획득 지점(`acquiredAt`)을 명시적으로 지정한다. 지정 가능한 값은 `reading_complete`, `board_stage_1`, `board_stage_2`, `board_stage_3` 이며, 해당 지점 도달 시 자동으로 획득된다.

**검증 가능한 충분성 조건**: 배틀 명제 P의 지지 전제 집합을 `premises(P)`라 할 때, 다음을 모두 만족해야 한다.

1. 각 전제 `p ∈ premises(P)`에 대해, `defeats === p.id`인 반례 카드가 **최소 1장 존재**한다.
2. 그 반례 카드의 `acquiredAt`이 배틀 진입 이전 지점(`reading_complete` 또는 `board_stage_*`)이다.
3. 어떤 반례 카드의 `defeats`도 존재하지 않는 전제 식별자를 가리키지 않는다.

이 조건은 콘텐츠 데이터만으로 자동 검증 가능하며, 불충족 시 실패로 처리한다(EC-08).

### BR-08. 보드 판정 모델 규칙

보드 퍼즐과 Sandbox의 판정 대상과 방법을 다음과 같이 고정한다. 이 규칙은 FR-03, FR-04, 13.2의 공통 기반이다.

1. **진리값의 귀속 단위**: 진리값은 사분면이 아니라 **하나의 행위 사례(φ)** 에 귀속된다. **사분면 자체는 진리값을 갖지 않는다.** 따라서 한 사분면에 여러 카드가 놓여도 판정에 간섭이 없다.
2. **진리값 벡터**: 각 행위 사례는 네 항의 진리값 벡터 `truth = {A, E, I, O}`(각 boolean)를 콘텐츠 데이터에 보유한다. 각 항의 의미는 φ에 대한 양상 주장이다 — A=□φ, E=□¬φ, I=◇φ, O=◇¬φ. 이 형식화는 `model` 등급 진술이다(BR-09).
3. **콘텐츠 정합성**: 모든 행위 사례의 `truth`는 BR-04의 여섯 관계를 전부 만족해야 한다. 즉 BR-04의 전수 귀결에 따라 `truth`는 세 정합 벡터 중 하나여야 한다. 위반 시 콘텐츠 검증 실패로 처리한다(EC-12).
4. **배치의 의미**: 사용자가 카드를 사분면 X에 놓는 행위는 "X항이 이 행위에 대해 참"이라는 주장으로 해석한다.
5. **배치 판정**:
   - `truth[X] === true` → **정합(consistent)**
   - `truth[X] === false` → **위반(inconsistent)**. 이때 X만 true로 바꾼 가상 벡터를 만들어, 활성 관계 중 성립하지 않는 관계를 열거해 사유로 제시한다.
6. **복수 정합의 처리**: `truth[X]`가 true인 사분면이 둘 이상일 수 있다. 예컨대 자유에 해당하는 행위는 I와 O가 모두 참이다. 이 경우 **어느 쪽에 놓아도 정합으로 판정**하며, 시스템은 복수 정합 사실과 그 논리적 의미를 안내한다(EC-11). 하나를 정답으로 강제하지 않는다. 이 처리는 G-2와 직결된다 — 사용자의 의문이 발생하는 지점을 은폐하지 않고 판정 규칙 안에 노출하기 위함이다.
7. **판정 함수의 단일성**: 보드 판정, Sandbox, 전수 검사는 **동일한 순수 함수** `evaluate(truthVector, activeRelationIds) → 관계별 성립/위반 결과`를 사용한다. 서로 다른 판정 경로를 두지 않는다.

### BR-09. 주장 등급(claimType) 규칙

콘텐츠의 모든 진술은 다음 세 등급 중 하나로 태깅하며, UI에서 구분 표시한다(FR-07).

| 등급 | 의미 | `src`의 역할 |
|---|---|---|
| `source` | 노트 원문에 문자 그대로 존재하는 진술 | 해당 진술의 위치 |
| `interpretation` | 원문을 해석·재구성한 진술 | 해석의 근거가 된 구간 |
| `model` | 게임 판정을 위해 채택한 형식화. 원문의 사실이 아니라 게임의 규약 | 그 형식화가 근거한 구간 |

**본 프로젝트에서의 적용**:

- 양상 개념과 법 개념의 대응(가능=정의로운 것 · 불가능=부정의한 것 · 필연=의무 · 우연=의무가 아닌 것)은 노트 127~135행에 명시되어 있으므로 **`source`**다.
- 이 대응을 양상 연산자로 형식화한 것(A=□φ, E=□¬φ, I=◇φ, O=◇¬φ)과, 그로부터 여섯 관계를 판정 규칙으로 삼는 것은 **`model`**이다. 원문은 도식과 그 관계명을 제시하지만 연산자 형식화를 제시하지 않는다.
- 사용자가 이의를 제기한 지점(노트 151행)에 대한 어떠한 결론도 `source`로 표기하지 않는다. Sandbox의 대조 진술(FR-04)은 `model`의 귀결로 표기한다.

이 규칙의 목적은 사용자가 **게임이 채택한 형식화를 원문의 사실로 오인하지 않게** 하는 것이며, 13.3의 사용자 수용 조건에 대응한다.

### BR-10. 콘텐츠 자기 검사 규칙

제품은 기동 시 내장 콘텐츠에 대해 다음 검사를 수행한다. 이 검사는 개발 시점의 사전 검증과 실행 시점의 자기 검사 양쪽에서 동일한 항목으로 수행된다.

| 항목 | 검사 내용 | 실패 시 |
|---|---|---|
| C-1 | 모든 엔티티가 `src`와 `claimType`을 보유 | EC-04 |
| C-2 | 모든 `src` 라인 범위가 내장 원문의 라인 수 범위 안에 존재 | EC-04 |
| C-3 | `sourceHash`가 내장 원문에서 계산한 해시와 일치 | EC-04 |
| C-4 | 모든 `BoardItem.truth`가 BR-04의 여섯 관계를 만족 | EC-12 |
| C-5 | 모든 `BoardStage.activeRelations`가 BR-04의 식별자 부분집합 | EC-12 |
| C-6 | BR-07의 충분성 조건 1~3 만족 | EC-08 |
| C-7 | `derivedFrom`이 비어 있지 않은 개념이 최소 1개 존재하고, 그 구성 개념이 모두 같은 챕터에 존재 | EC-12 |
| C-8 | 모든 식별자 참조(`defeats`, `derivedFrom`, 단계별 카드 목록)가 실재하는 식별자를 가리킴 | EC-12 |

검사 실패 시 제품은 해당 챕터를 플레이 가능 상태로 표시하지 않고, 실패 항목을 진단 정보로 표시한다. 검사를 통과하지 않은 콘텐츠는 배포하지 않는다.

| 흐름 단계 | 대응 화면 상태 | 게이팅 |
|---|---|---|

### 6.2 Data States

**계층 관계**: 흐름 단계 3(보드 퍼즐)은 내부에 퍼즐 단계 1·2·3을 가진다. 즉 `흐름 단계 3.done ⟺ 모든 퍼즐 단계가 cleared`이다. 두 계층은 독립된 상태가 아니라 포함 관계다.

| 데이터 | 상태 | 전이 조건 |
|---|---|---|
| 챕터 | `locked` → `in_progress` → `completed` | 진입 시 / 결산 도달 시 |
| 흐름 단계(1~6) | `inactive` → `active` → `done` | 직전 단계 `done` 시 활성화 (BR-05) |
| 퍼즐 단계(1·2·3) | `inactive` → `active` → `cleared` | 모든 카드 배치 + 모든 카드 정합 시 `cleared` (FR-03, BR-08) |
| 개념 카드 | `unacquired` → `acquired` | 리딩 완료 또는 합성 성공 |
| 반례 카드 | `unacquired` → `acquired` | `acquiredAt` 지점 도달 (BR-07) |
| 카드 배치 | `unplaced` → `placed(X)` | 사용자 배치. 재배치로 X 변경 가능 |
| 카드 판정 | `consistent` / `inconsistent` | `truth[X]` 값에 따름 (BR-08) |
| 관계선 | `inactive` / `satisfied` / `violated` | 활성 집합 및 기준 카드 벡터에 따름 |
| 전제 | `standing` → `defeated` | `defeats` 식별자 일치 반례 적중 |
| 명제 | `standing` → `collapsed` | 지지 전제가 모두 `defeated` |
| 미결 사건 | `open` → `resolved` | 논거 1장 이상 선택 + 서술 20자 이상 (FR-06) |

## 7. Data Lifecycle & Persistence

### 7.1 Data Ownership

콘텐츠 데이터(`ChapterContent`, `SourceText`)는 제품에 내장된 읽기 전용 데이터다. 진행 상태와 사용자 서술(`GameState`)은 전적으로 사용자에게 귀속된다.

### 7.2 Storage

- 서버를 사용하지 않는다. 모든 데이터는 사용자의 실행 환경에 머문다.
- 콘텐츠 데이터와 원문 텍스트는 단일 HTML 문서 내부에 포함된다(BR-06).
- 진행 상태는 메모리의 단일 `GameState` 객체로 유지한다.
- 브라우저 저장소를 사용할 수 있는 환경에서는 보조 저장 수단으로 사용하며, 저장 단위는 `GameState` 전체다.
- 사용자가 명시적으로 내보낸 JSON 파일 및 「나의 정의론」 Markdown 파일이 1차 보존 수단이다.

### 7.3 Synchronization

서버가 없으므로 동기화 정책은 해당 없음. 서로 다른 환경 간 이동은 JSON 내보내기/불러오기로 수행한다.

### 7.4 Retention

내보낸 파일은 사용자가 보관하는 한 무기한 보존된다. 메모리 상태는 페이지 종료 시 소멸하며, 보조 저장소 사용이 가능한 환경에서는 해당 저장소의 수명을 따른다.

### 7.5 Deletion

- 사용자가 브라우저 저장소를 삭제하면 보조 저장분이 삭제된다.
- 페이지를 종료하면 메모리 상태가 소멸한다.
- **미저장 이탈 경고의 적용 범위**: 경고는 브라우저의 페이지 이탈 직전 이벤트에 한해 시도한다. 대상은 탭·창 닫기, 새로고침, 주소 이동이다. 브라우저 정책상 **경고 문구를 제품이 지정할 수 없고 표시 여부도 브라우저가 결정**하므로, 이 경고는 보조 수단으로만 취급한다. 제품은 이와 별개로 **미저장 서술이 존재하는 동안 화면에 상시 표시되는 저장 안내**를 제공하며, 이것이 보장되는 수단이다(EC-02).
- 내보낸 파일의 삭제는 사용자의 파일 시스템에서 수행되며 제품의 관여 대상이 아니다.

## 8. Error & Edge Cases

### EC-01. 브라우저 저장소 사용 불가

- **발생 조건**: 실행 환경이 브라우저 저장소를 지원하지 않거나 접근이 차단된 경우. `file://` 실행 환경에서 발생할 수 있다.
- **시스템 상태**: 메모리 상태만으로 정상 동작한다.
- **표시**: 자동 저장이 불가하며 내보내기로 보존해야 함을 상시 안내한다.
- **데이터 처리**: 보조 저장을 시도하지 않고 내보내기/불러오기 방식으로 폴백한다.
- **복구 정책**: 재시도하지 않는다.
- **최종 상태**: 게임은 전 기능 정상 동작하며, 보존은 사용자 내보내기에 의존한다.

### EC-02. 미저장 서술 보유 상태에서의 이탈

- **발생 조건**: 사용자 서술이 입력·변경되었으나 내보내기 또는 보조 저장이 수행되지 않은 상태.
- **시스템 상태**: 이탈 전 상태 유지.
- **표시**: ① 미저장 상태 동안 화면에 상시 저장 안내를 표시한다(보장 수단). ② 페이지 이탈 직전 이벤트에서 브라우저 표준 경고를 시도한다(보조 수단, 문구 지정 불가·표시 보장 불가).
- **데이터 처리**: 별도 처리 없음.
- **복구 정책**: 사용자가 잔류를 선택하면 내보내기 수단으로 안내한다.
- **최종 상태**: 사용자가 이탈을 확정하면 메모리 상태는 소멸한다.

### EC-03. 불러온 진행 상태 파일의 검증 실패

- **발생 조건**: FR-10의 검증 순서 ①~⑤ 중 하나 이상 실패.
- **시스템 상태**: 기존 진행 상태와 내장 콘텐츠를 그대로 유지한다.
- **표시**: 실패한 검증 단계와 사유를 구분해 표시한다(파싱 실패 / 스키마 버전 불일치 / 원문 버전 불일치 / 필드 오류 / 참조 무결성 오류).
- **데이터 처리**: 부분 적용을 하지 않는다. 전부 적용 또는 전부 미적용.
- **복구 정책**: 다른 파일로 재시도할 수 있다.
- **최종 상태**: 불러오기 이전 상태가 보존된다.

### EC-04. 원문 근거 무결성 실패

- **발생 조건**: BR-10의 C-1, C-2, C-3 중 하나 이상 실패.
- **시스템 상태**: 해당 챕터를 플레이 가능 상태로 표시하지 않는다.
- **표시**: 실패 항목과 대상 엔티티 식별자를 진단 정보로 표시한다.
- **데이터 처리**: 검증 실패로 보고한다.
- **복구 정책**: 콘텐츠 수정으로만 해소된다.
- **최종 상태**: 검사를 통과한 콘텐츠만 배포·플레이된다.

### EC-05. 포인터 드래그가 동작하지 않는 환경

- **발생 조건**: 입력 장치나 브라우저 제약으로 드래그가 불가능함.
- **시스템 상태**: 정상.
- **표시**: 탭 기반 경로로 동일한 조작이 가능하다(FR-11).
- **데이터 처리**: 동일.
- **복구 정책**: 해당 없음.
- **최종 상태**: 입력 방식과 무관하게 동일한 판정 결과에 도달한다.

### EC-06. 웹폰트 로딩 실패

- **발생 조건**: 네트워크 미연결, `file://` 실행, 또는 폰트 리소스 접근 실패.
- **시스템 상태**: 정상.
- **표시**: 시스템 폰트로 렌더링되며 기능 제약은 없다.
- **데이터 처리**: 해당 없음.
- **복구 정책**: 재시도하지 않는다.
- **최종 상태**: 레이아웃이 깨지지 않고 콘텐츠가 가독 가능한 상태를 유지한다.

### EC-07. Sandbox에서의 논리적 모순 설정

- **발생 조건**: 사용자가 정합하지 않은 벡터(16가지 중 13가지)를 설정함.
- **시스템 상태**: 정상. 이는 오류가 아니라 Sandbox의 의도된 기능이다(FR-04).
- **표시**: 위반된 관계와 그 조건문, 그리고 "이 조합을 만족하는 행위는 존재할 수 없음"을 표시한다.
- **데이터 처리**: 설정을 차단하거나 되돌리지 않는다.
- **복구 정책**: 해당 없음.
- **최종 상태**: 사용자가 위반 내역을 확인한 상태.

### EC-08. 반례 카드 충분성 조건 미충족

- **발생 조건**: BR-10의 C-6 실패. 즉 어떤 전제를 무너뜨릴 반례가 없거나, 반례의 `acquiredAt`이 배틀 이후이거나, `defeats`가 존재하지 않는 전제를 가리킴.
- **시스템 상태**: 해당 챕터를 플레이 가능 상태로 표시하지 않는다.
- **표시**: 충족되지 않은 조건 번호와 대상 전제·반례 식별자를 진단 정보로 표시한다.
- **데이터 처리**: 검증 실패로 보고한다.
- **복구 정책**: 콘텐츠 수정으로만 해소된다.
- **최종 상태**: 배틀 진입 시 필요한 반례가 전량 확보되는 구성만 배포된다.

### EC-09. 퍼즐 단계 미완료 상태에서의 진행 시도

- **발생 조건**: 미배치 카드가 있거나 위반 판정된 카드가 남은 상태에서 다음 단계 진행이 시도됨.
- **시스템 상태**: 현재 단계 유지.
- **표시**: 미충족 조건을 구분해 표시한다(미배치 카드 목록 / 위반 카드 목록과 각각의 위반 관계).
- **데이터 처리**: 배치 상태를 초기화하지 않는다.
- **복구 정책**: 사용자가 재배치로 해소한다. 시도 횟수 제한은 없다.
- **최종 상태**: 클리어 조건 충족 시에만 단계가 `cleared`로 전이한다.

### EC-10. 카드 배치 위반

- **발생 조건**: 사용자가 카드를 `truth[X] === false`인 사분면 X에 배치함(BR-08).
- **시스템 상태**: 배치 자체는 유지된다. 카드가 `inconsistent`로 표시된다.
- **표시**: X를 참으로 가정했을 때 위반되는 활성 관계 목록과 각 관계의 조건문을 표시한다. 문구는 BR-02를 따른다.
- **데이터 처리**: 배치를 되돌리거나 차단하지 않는다.
- **복구 정책**: 사용자가 재배치한다.
- **최종 상태**: 모든 카드가 `consistent`가 되면 단계가 성립한다.

### EC-11. 복수 정합 배치

- **발생 조건**: 카드의 `truth`에서 참인 항이 둘 이상이며, 사용자가 그중 하나에 배치함(BR-08의 6항). 자유에 해당하는 행위(I=T, O=T)가 이에 해당한다.
- **시스템 상태**: 정합으로 판정한다. 이는 오류가 아니다.
- **표시**: 복수의 항이 참이라는 사실, 참인 항의 목록, 그리고 그것이 의미하는 상태(자유)를 표시한다. 다른 항을 정답으로 제시하지 않는다.
- **데이터 처리**: 배치를 변경하지 않는다.
- **복구 정책**: 해당 없음.
- **최종 상태**: 사용자가 복수 정합의 의미를 확인한 상태. 이 안내는 미결 사건(FR-06)의 논의 대상과 직접 연결된다.

### EC-12. 콘텐츠 구조 무결성 실패

- **발생 조건**: BR-10의 C-4, C-5, C-7, C-8 중 하나 이상 실패.
- **시스템 상태**: 해당 챕터를 플레이 가능 상태로 표시하지 않는다.
- **표시**: 실패 항목과 대상 식별자를 진단 정보로 표시한다.
- **데이터 처리**: 검증 실패로 보고한다.
- **복구 정책**: 콘텐츠 수정으로만 해소된다.
- **최종 상태**: 검사를 통과한 콘텐츠만 배포·플레이된다.

## 10. Non-Functional Requirements

### NFR-01. Compatibility

- **최소 지원 기준**: ES2020 문법과 표준 DOM·SVG·Pointer Events·File API를 지원하는 브라우저. 구체적으로 데스크톱 및 모바일의 Chromium 계열, Firefox, Safari 각각의 **최신 2개 메이저 버전**을 지원 대상으로 한다.
- 트랜스파일 및 폴리필을 사용하지 않는다(빌드 단계 부재, 12.1).
- 빌드 도구 없이 브라우저에서 단일 HTML 파일을 여는 것만으로 실행되어야 한다.
- `file://` 프로토콜로 직접 열었을 때 전 기능이 동작해야 한다. 단, 브라우저 저장소는 EC-01에 따라 폴백하며, 이탈 경고는 7.5에 따라 보조 수단으로 취급한다.
- 네트워크 연결이 없어도 전 기능이 동작해야 한다.

### NFR-02. Performance

- 카드 드래그·재배치 및 관계선 갱신은 **프레임당 16ms 이내**에 처리되어야 한다.
- 판정 함수 `evaluate` 1회 호출은 **1ms 이내**에 완료되어야 한다.
- 챕터 진입부터 첫 리딩 카드 표시까지 **1초 이내**여야 한다.
- 개념 지도는 사전 지정 좌표를 사용하므로 레이아웃 연산이 발생하지 않아야 한다.
- 콘텐츠와 원문이 문서 내부에 포함되므로, 초기 로드 이후 데이터 취득 대기가 발생하지 않아야 한다.

### NFR-03. Maintainability

- **섹션 구분 규약**: 단일 HTML 문서는 다음 순서의 최상위 영역으로 구성하며, 각 영역의 시작과 끝을 고정 형식의 주석 마커(`/* ==== SECTION: <이름> ==== */`)로 표시한다.
  1. `STYLE-TOKENS` (디자인 토큰)
  2. `STYLE-COMPONENTS`
  3. `MARKUP`
  4. `DATA-SOURCE-TEXT` (내장 원문)
  5. `DATA-CHAPTER-CONTENT` (챕터 콘텐츠, 챕터별로 하위 마커 분리)
  6. `ENGINE-RULES` (BR-04 규칙 테이블 및 `evaluate`)
  7. `ENGINE-STATE`
  8. `ENGINE-VALIDATION` (BR-10 자기 검사)
  9. `UI-*` (화면별)
  10. `BOOTSTRAP`
- 콘텐츠 데이터 영역(4~5)에는 로직을 두지 않고, 엔진 영역(6~8)에는 챕터 고유 값을 두지 않는다(BR-03).
- 판정은 부수 효과 없는 순수 함수로 구현하여 독립적으로 검증 가능해야 한다.

### NFR-04. Scalability

- 챕터 추가가 `DATA-CHAPTER-CONTENT` 영역의 데이터 블록 추가만으로 가능해야 한다(BR-03, BR-06).
- 엔진 코드는 특정 챕터의 내용에 의존하지 않아야 한다.
- 퍼즐 단계 수와 각 단계의 활성 관계 집합은 `stages` 배열로 결정되어야 하며, 엔진에 3단계가 고정되어서는 안 된다.
- 후속 단계의 React + Vite + TypeScript 이관 시 판정 로직과 콘텐츠가 재작성 없이 이식 가능해야 한다.

### NFR-05. Accessibility

- 색상에 의존하지 않고 관계 유형, 활성/비활성, 정합/위반, `claimType`이 구별되어야 한다.
- 드래그 없이 모든 조작이 완료 가능해야 한다.
- 사용자의 모션 감소 설정을 존중해야 한다.

### NFR-06. Reliability

- 진행 상태 불러오기는 전부 적용 또는 전부 미적용으로 처리하여 부분 손상 상태를 만들지 않아야 한다.
- 저장소 접근 실패가 게임 진행을 중단시키지 않아야 한다.
- **콘텐츠 자기 검사(BR-10)는 개발 시점과 실행 시점 양쪽에서 동일한 항목으로 수행**하며, 실행 시 실패하면 해당 챕터를 플레이 불가로 표시하고 진단 정보를 남긴다. 검사를 통과하지 않은 콘텐츠는 배포하지 않는다.

## 12. Technical Constraints & Approved Technical Decisions

### 12.1 Technical Constraints

- 파일럿 산출물은 **외부 의존성 없는 단일 HTML 파일**이어야 한다.
- 빌드 단계를 실행 조건으로 요구해서는 안 되며, 트랜스파일·폴리필을 사용하지 않는다.
- 서버 및 백엔드를 사용하지 않는다.
- `file://` 실행 환경을 전제하며, 제품이 스스로 개시하는 외부 리소스 취득을 실행 경로에 두어서는 안 된다(BR-06).
- 브라우저 저장소를 필수 의존 대상으로 삼아서는 안 된다(EC-01).
- 3장 콘텐츠 JSON이 사용자 검토로 확정되기 전에는 엔진 구현에 착수하지 않는다(3.1).

### 12.2 Approved Technical Decisions

- 파일럿은 단일 HTML, 확장 단계에서 React + Vite + TypeScript로 이관하는 2단계 전략을 채택한다.
- 엔진과 콘텐츠를 소스 수준에서 분리하고, 챕터를 6.3의 JSON 스키마로 정의한다(BR-03).
- **콘텐츠 데이터와 원문 텍스트는 단일 HTML 문서 내부의 인라인 데이터 블록으로 포함한다.** 챕터 추가·교체는 이 블록의 추가·교체로 수행하며 엔진 코드를 수정하지 않는다(BR-06).
- **외부 콘텐츠 JSON 로드는 파일럿 범위에서 제외한다**(3.2). 사용자 파일 선택은 진행 상태 불러오기에만 사용한다.
- 모든 콘텐츠 스키마에 `src`와 `claimType` 필드를 필수로 둔다(BR-01, BR-09).
- 콘텐츠 루트에 `sourceVersion`과 `sourceHash`를 두고 원문 버전을 결박한다(BR-01).
- 반례 카드는 `acquiredAt`으로 획득 지점을 명시하며, BR-07의 충분성 조건을 자동 검증한다.
- **보드 판정은 BR-08의 모델을 따른다.** 진리값은 행위 사례에 귀속되고, 사분면은 진리값을 갖지 않으며, 보드·Sandbox·전수 검사가 동일한 순수 함수 `evaluate(truthVector, activeRelationIds)`를 사용한다.
- 복수 정합 배치는 오류가 아니며 하나를 정답으로 강제하지 않는다(EC-11).
- 퍼즐 단계 수와 단계별 활성 관계 집합은 콘텐츠 데이터의 `stages`로 선언한다.
- 반례 배틀은 체력 방식이 아닌 전제 붕괴 구조로 구현하며, 적중 판정은 식별자 문자열 일치로 한다.
- 대당 사각형 보드와 개념 지도는 SVG로, 카드는 DOM/CSS로 렌더링한다.
- 드래그는 표준 Drag & Drop API가 아닌 포인터 이벤트 기반 커스텀 구현을 사용한다.
- 관계선은 색상이 아닌 선 스타일로 구분하고, 활성/비활성은 두께와 불투명도로 구분한다.
- 개념 지도는 물리 시뮬레이션이 아닌 사전 지정 좌표를 사용한다.
- 저장은 메모리 상태 + JSON 내보내기/불러오기를 기본으로 하고, 브라우저 저장소는 보조 수단으로 한다. 상태 파일은 `schemaVersion`과 `sourceVersion`을 포함한다.
- 아트 디렉션은 "이성의 기하학"을 따른다: 양피지 아이보리 배경과 잉크 블랙 본문, 세피아 골드 포인트, 로열 블루(필연·진리)/버건디(모순·부정의)/청록(허용)의 상태색, 다크모드는 딥 네이비와 촛불 앰버. 국문 본문은 산세리프, 개념명과 라틴어는 세리프로 대비한다. 대당 사각형 도형을 UI 반복 모티프로 사용한다. 웹폰트를 사용할 경우 시스템 폰트 폴백을 반드시 지정한다(EC-06).
- 3장 콘텐츠 JSON은 AI가 초안을 작성하고 사용자가 검토·수정하는 방식으로 제작하며, Development AI가 값을 생성하지 않는다.
- 제작 순서는 다음 8단계를 따르며, 콘텐츠 JSON 확정이 엔진 구현보다 선행한다.
  1. 디자인 토큰 및 레이아웃 골격
  2. **3장 콘텐츠 JSON 작성 및 사용자 검토 확정** (단계별 활성 관계, `BoardItem.truth`, `acquiredAt`, `claimType`, `derivedFrom` 포함)
  3. 리딩 뷰 및 개념 카드 획득
  4. 판정 엔진(`evaluate`) 및 보드 퍼즐
  5. 반례 배틀
  6. 내 의문 노트 및 Sandbox, 내보내기
  7. 개념 지도 및 결산
  8. 접근성·모션·검증
- 검증은 16가지 전수 검사, BR-10의 자기 검사 8항목을 포함한다.

### 12.3 Implementation Freedom

위에서 명시되지 않은 내부 구현 세부사항은, [P-1]의 APPROVED 및 그로부터 재구성된 본 명세의 내용을 위배하지 않는 한 Development AI가 합리적으로 결정할 수 있다. 클래스명, 함수명, 내부 파일 구조, 알고리즘, 라이브러리 선택 등은 별도의 승인된 요구사항이 없는 한 본 PRD에서 강제하지 않는다.

**Implementation Freedom에서 제외되는 항목(임의 결정 금지)**: 아래는 제품 동작을 규정하는 핵심 사항이므로 본 명세에 정의된 대로 구현해야 하며, Development AI가 달리 결정하거나 미정의 상태로 두어서는 안 된다.

1. 보드 판정 모델 — 진리값의 귀속 단위, 배치의 의미, 정합/위반 판정, 복수 정합 처리 (BR-08)
2. 관계 규칙 테이블과 판정 함수의 단일성 (BR-04, BR-08의 7항)
3. 콘텐츠 JSON 스키마 및 진행 상태 스키마 (6.3)
4. 콘텐츠 데이터의 값 자체 — 값은 확정된 콘텐츠에서 가져오며 생성·보충하지 않는다 (3.1)
5. 리딩 카드 소비 판정 기준 (FR-01)
6. 미결 사건 `resolved` 전이 조건 (FR-06)
7. 「나의 정의론」 Markdown 출력 구조 (FR-09)
8. 진행 상태 불러오기 검증 순서와 실패 처리 (FR-10)
9. `claimType` 등급 체계와 그 표시 (BR-09)
10. 콘텐츠 자기 검사 항목 (BR-10)

## 13. Acceptance Criteria

### 13.1 Functional Acceptance

- FR-01 ~ FR-11의 각 Acceptance Criteria가 모두 충족된다.
- 6단계 흐름이 BR-05의 게이팅 규칙대로 순차 활성화되고, 6.1의 흐름–화면 대응표대로 전이한다.
- **보드 판정이 BR-08대로 동작한다.** 구체적으로 ① 한 사분면에 복수 카드를 놓아도 각 카드가 독립 판정된다. ② `truth[X]`가 참인 배치는 정합, 거짓인 배치는 위반으로 판정되고 위반 관계가 열거된다. ③ 참인 항이 둘 이상인 카드는 어느 쪽에 놓아도 정합으로 판정되며 복수 정합이 안내된다.
- 보드 퍼즐 1·2·3단계의 활성 관계 수가 각각 2·4·6이며, 클리어 조건이 FR-03대로 판정된다.
- Sandbox가 FR-04의 출력 규칙 네 가지를 모두 표시하며, I·O 대조표에서 (F,F)가 성립 불가로 표시된다.
- 배틀에 필요한 반례 카드가 모두 배틀 진입 이전 지점에서 획득된다(BR-07).
- 모든 콘텐츠 엔티티가 `src`와 `claimType`을 보유하며, 원문 보기와 등급 배지가 동작한다(BR-01, BR-09).
- 판정 문구가 "정답"이 아닌 "채택된 형식 모델에서의 귀결"로 표기된다(BR-02).
- 미결 사건이 논거 1장 이상 + 서술 20자 이상일 때만 `resolved`로 전이한다.
- 「나의 정의론」이 FR-09의 절 순서대로 출력된다.

### 13.2 System Acceptance

- 3장 파일럿을 진입부터 결산까지 중단 없이 완주할 수 있다.
- **`file://` 프로토콜로 파일을 직접 열었을 때 전 과정이 동작하며, 제품이 개시하는 외부 리소스 취득이 발생하지 않는다.**
- 5종 메커니즘(정의 합성, 대당 사각형 퍼즐, 반례 배틀, 내 의문 노트, 개념 지도)이 하나의 흐름 안에서 함께 동작한다.
- **판정 함수의 단일성이 확인된다.** 보드 판정, Sandbox, 전수 검사가 동일한 함수를 호출한다.
- **전수 검사 결과가 BR-04의 고정 사실과 일치한다.** 여섯 관계를 모두 적용할 때 16가지 조합 중 정합이 정확히 3가지이며, 그 벡터가 ⟨T,F,T,F⟩·⟨F,T,F,T⟩·⟨F,F,T,T⟩이다. 활성 관계 집합을 부분집합으로 주면 해당 관계만 판정에 반영된다.
- 콘텐츠 데이터 블록을 추가·교체하는 것만으로 다른 챕터 구성이 로드되며, 엔진 코드 수정이 요구되지 않는다(BR-03 검증).
- **BR-10의 자기 검사 8개 항목(C-1~C-8)이 전부 통과 상태**이며, 각 항목이 의도적으로 위반된 콘텐츠에 대해서는 해당 항목이 실패로 검출된다.
- NFR-01의 지원 브라우저 범위에서 위 조건이 성립한다.
- 브라우저 저장소를 사용할 수 없는 환경에서도 완주와 내보내기가 가능하다.

### 13.3 User Acceptance

- 사용자가 노트 3장을 줄글로 읽지 않고도 대당 사각형의 네 항과 여섯 관계를 조작으로 파악할 수 있다.
- 사용자가 퍼즐 1단계에서 3단계로 진행하면서 관계가 점진적으로 추가되는 것을 체감할 수 있다.
- **사용자가 「가능성과 우연성은 동치인가」에 대해 Sandbox 조작 결과에 근거해 두 가지를 각각 진술할 수 있다.** ① I=T·O=F인 정합 벡터(의무)가 존재하므로 둘은 동치가 아니다. ② 자유에 해당하는 행위에서는 둘이 함께 참이므로 동치처럼 보인다.
- **사용자가 게임이 제시한 형식화(`model` 등급)를 원문의 사실(`source` 등급)로 오인하지 않는다.** 구체적으로, 양상 연산자 형식화가 노트 원문에 문자 그대로 존재하지 않는다는 사실을 게임 내에서 확인할 수 있다.
- 사용자가 반례 배틀에서 자신이 노트에 남긴 반문("불가능하다 해서 의무가 아니게 되는가?")을 직접 무기로 사용하는 경험을 한다.
- 사용자가 해당 의문에 대한 자기 결론을 서술하고, 「나의 정의론」 Markdown으로 내보내 원래 노트에 병합할 수 있다.
